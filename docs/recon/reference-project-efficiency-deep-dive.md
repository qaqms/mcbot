## 1. 往返经济学（round-trip economics）

**一次任务花几次调用 —— 这是全仓最贵的常数。**
- 主请求实测区间 **18k–33k token**，注解理由是「38 个工具的 schema + 系统提示 + 全部历史」；
  长期目标硬线 **30 轮**，注解写明「30 轮已经六十万起」。出处：`api/common/.../agent/goal/GoalState.java:26-34`。
- **无工具回合硬上限（有意为之）**：`ConvoState` 头部注明没有循环守卫、没有轮数上限，
  且曾有一个「同签名重复调用」的循环检测器把**正确的超时重派**误杀（中途超时后续跑同一个 `move_to`），
  因此被移除。失控交给主人中断 + 目标轮数。出处：`ai/.../agent/llm/ConvoState.java:19-25`。
  同一决定在开轮处复述：`api/common/.../client/.../agent/EntityAgentLoop.java:1288-1291`。
- **一回合内多个工具调用一次收下、串行执行**：响应里 `toolCalls()` 整批交给派发器，
  `dispatch(List, callable)` 后才逐个跑。这省掉的是「一个动作一次模型往返」的放大效应：
  模型可以在一次响应里编排一串动作。出处：`EntityAgentLoop.java:1956-1958`；
  `ToolDispatcher.java:95-99`。
- **派发器是严格串行单槽**（`inFlight` ≤1，`Deque` 排队），下一件只在上一件结果落地后派。
  出处：`ToolDispatcher.java:59-68, 151-197`。⇒ 这就是它**必须**把无界长活做成异步的原因（见 §7）。
- **超时兜底极宽**：单件在飞工具墙钟兜底 **15 分钟**（`15*60*1000`），注释写明"只救死服务端"，
  核心工具永不触发。出处：`ToolDispatcher.java:54`。
- **⚠ 但这个兜底只在客户端 tick 里被检查**（`clientTick()` → 派发器 `tick()`），
  **没有 tick 就永远不会触发**——一个永不返回的工具会把回合永久挂住。
  同一条客户端 tick 通道还负责：队列的"条数/时长"成熟度自动排空（急件是 push 时直接叫醒，不受影响）。
  出处：`EntityAgentLoop.java:496-503, 500-502, 1067`。⇒ **这正是 mcbot 缺失的那类依赖**（见文末"依赖告警"）。
- **两段时间纪律**：客户端是宽松墙钟兜底（15 分钟），服务端是**紧的、以游戏刻计、且冻结感知的期限**——
  被抢占一 tick 就把期限推后一 tick（等待规划器在飞时同样推后），因此"被本能抢占"不会被误判成超时。
  出处：`task/TaskSlot.java:110-115`、`task/base/AbstractCompanionTask.java:133-140`。
- **收尾顶替往返**：任务完成走事件而非工具结果，且该事件按队列三态路由自动落进"立刻开轮"档，
  因此"不是新增开销，而是替代旧同步模式里最后那次结果往返"。出处：`the mind-model architecture doc:116-119`。
- **禁用轮询**：提示词与文档双处写明"NEVER poll，完成必然主动送达；timeout 事件携带进度，重派同一调用可续做"。
  出处：`ai/.../agent/prompt/the static-prompt class:56-63`、`the mind-model architecture doc:126`。
- **替换式受理省一轮**：注入模型的 `<current_task>` 明确告诉它"派新活直接顶掉旧活，不需要先 stop"，
  理由写得很具体——**说成"别再派"会让模型先 stop 再派，白跑一轮**。出处：`EntityAgentLoop.java:1570-1580`。
- **目标评估器是另一次独立小调用**：不带工具、不带人设、不带历史，只喂目标条件 + 身体事实 + 目标以来发生的事；
  窗口 **8000 字符**上限、**每行截断 400 字符**；只把 `freshTokens()`（缓存读不计）记进目标账。
  出处：`EntityAgentLoop.java:98-100, 667-682`、`GoalPrompts.java:69-121`。
- **目标正文只说一次**：注释直接点出成本模型——整份目标每轮重发会进历史，而历史每轮全量重发，
  于是 **O(n²)**；因此只在设定时发一次，之后每轮只补一句"还差什么"。
  出处：`GoalPrompts.java:5-14, 36-58`。
- **失败要教人**（纯提示词收益）：工具失败文案必须写"为什么失败 + 通常的下一步"，
  并明令"照着改，不要原样重发"。出处：`the static-prompt class:53-55`。
- **每轮一次的重试而非多次**：传输层自己退避（见下），回合层只在**流中途死亡**时重跑**一次**整轮，`turnRetried` 复位于响应落地。
  出处：`EntityAgentLoop.java:1858-1878`。
- **压缩调用也是模型调用**，token 计入累计。出处：`EntityAgentLoop.java:1431`。

**传输层参数（`ai/.../agent/http/HttpLlmTransport.java`）**
- 连接超时 **10s**；请求超时 **120s**（:54-55）。
- 重试 **2 次**，退避 `min(500ms × 2ⁿ, 8000ms)`，**抖动最多减去 25%**（:59-61, 305-309）；
  `Retry-After` **仅在 `0 < v ≤ 60000 ms` 时才被采纳**（:234-236, 293-303）；
  可重试集合 = `x-should-retry` 头覆盖，否则 408/409/429/5xx（:281-288）。
- **重试只发生在首个 chunk 送达之前**（:213, 233）。
- **SSE 块间空闲看门狗 90s**，单守护线程；理由是 JDK 请求超时只覆盖到响应头，卡死的 body 会永久挂住（:62-73）。
- **首个流事件送达后绝不重试**（token 已消耗）；重试只在流开始前。⇒ 证据：`docs/recon` §5.2 已记，此处不重复展开。

**可迁移**：macro 层最划算的三条是「(a) 一次响应批多个动作」「(b) 长活受理即回执 + 收尾走事件」「(c) 目标/判定类小调用独立成便宜请求」；
mcbot 已有 R2-A 早派发，比参考项目更靠前，**不要回退**成"整条流结束才派"。
**⇒ transferable to mcbot:** 把 mcbot 现有的"每步一次往返"改成"一次响应批量动作"需先扩 `ToolRegistry` 支持同批多调用
（mcbot 已有 `ServerToolDispatcher` 三道闸，天然可做逐条受理）；另建议把 mcbot 的 `/goal` 类判定抽成
独立小请求（无工具、无历史、窗口 ≤8k 字符、每行 ≤400 字符），并按 `fresh`（不含缓存读）记账。

## 2. 提示词 / 缓存经济学

**稳定层（进系统提示，必须逐字节稳定）**：人设区块 + 操作核心（静态常量文本）+ 技能目录 XML
+ 本能名册 + **延迟工具目录**（每工具一行摘要，**摘要上限 96 字符**，取描述第一句）。
出处：`EntityAgentLoop.java:1740-1775`、`agent/tool/ToolDisclosure.java:38-39, 103-135`。
- **恒定排序是硬要求**：目录"顺序随注册顺序，同一组工具两次生成必须逐字节相同，否则系统提示不稳定，前缀缓存白瞎"。
  出处：`ToolDisclosure.java:99-102`。
- **工具 schema 是缓存前缀的一部分**：常驻工具完整定义每轮随请求发；其余只在系统提示留一行摘要，
  模型调 `find_tools` 才取回完整定义——"省的是每一轮的输入，不是一次性的"。
  出处：`ToolDisclosure.java:19-22`。
- 常驻（RESIDENT）工具仅 9 个：`find_tools` / `load_skill` / `todowrite` / `get_self_status` /
  `inspect_block` / `look_around` / `scan_blocks` / `scan_nearby_entities` / `goto`；
  **其余全部默认延迟**（工具基类的驻留声明 缺省 DEFERRED）。出处：各工具类的 `residency()` 覆写，
  默认见 `agent/tool/the tool base interface:28-36`。

**刻意排除在系统提示之外、改为按轮注入的**：
- `<known_blocks>`（已放置/使用过的工作站）——理由是它随放置/使用而变，放系统提示会打碎前缀缓存。
  出处：`EntityAgentLoop.java:1225-1234`。
- `<runtime_state>` 信封：`<current_task>` + `<inventory>` + `<effects>` + `<riding>` + 插件贡献的每轮片段。
  全部现算，**一个字都不入会话历史**。出处：`EntityAgentLoop.java:1542-1560`。
  - 效果块的理由最锋利：它带倒计时，沉进历史后十轮再读到的是"一个理直气壮的错秒数"（:1626-1638）。
  - **空块不发**："空块也是要读的 token，而'没写'和'写了没有'对模型是一样的"（:1630）。
  - 插件状态片段明确"和背包、buff 一样是此刻的她，会变，所以不能进字节级稳定的系统提示"（:1547-1550）。
- **背包块的出现是为了省一整轮**：注释写明"放进请求而不是让她调 `get_self_status`，
  省的是**一整轮**（请求 + 工具结果 + 再请求）"；合并同类计数、不报耐久附魔（要精确到槽位才调 `inspect_gui`）。
  出处：`EntityAgentLoop.java:1599-1601, 1676-1698`。
- 背包块有**身份缓存**：只在服务端推来**新的快照对象**时重渲染（比对象身份，不用时间戳凑版本号）。
  出处：`EntityAgentLoop.java:1588-1618`。

**缓存浪费诊断器（逐轮计算，不是统计）**
- 定义：`漏掉的 = min(上轮提示词, 本轮提示词) − 本轮缓存读`。
- **噪声底 1024 token**（低于此的差额算缓存分段粒度噪声，不计）。
- 三种情况不计：没有上一轮；本轮无提示词；**本轮完全无缓存活动且此前也从未有过**
  （为了区分"缓存没命中"和"这家服务商根本不报缓存"，否则后者每轮都被误判成全量漏掉）。
- 历史被剪断（压缩/清空）后 `reset()`，从下一轮重新起算。
- 刻意**不折算金额**（价格表维护不起）；**累计式不存历史**（只需上一轮的提示词体量）。
- 出处：`ai/.../agent/provider/CacheWaste.java:20-64`；判据逐条钉死在
  `ai/src/test/.../provider/CacheWasteTest.java`（含"从不报缓存的服务商不被指控"用例）。

**用量四元拆分（唯一与厂商无关的拆法）**
`input`（真正新处理）/ `cacheRead` / `cacheWrite` / `output`，三者相加 = `promptTokens`；
`fresh = input + cacheWrite + output`（**缓存读近乎免费不计，缓存写是实打实处理过的计**）；
`cacheHitRate = cacheRead / promptTokens`，无提示词时返回 **−1**——"'没数据'和'命中率 0%'是两回事"。
出处：`ai/.../agent/provider/Usage.java:16-50`。
- **命中率看最近一轮，不看累计**：注释理由是"累计命中率会被历史稀释，看不出刚才那轮把缓存打穿了"。
  出处：`api/common/.../client/.../agent/TokenLedger.java:20-22, 45-48`。
- 各家方言归一：OpenAI 从 `prompt_tokens_details.cached_tokens` 反推 `input = prompt − cached`；
  Anthropic 的缓存写单独保留；DeepSeek 用自家 hit/miss 字段。出处：`UsageAccountingTest.java:23-71`。

**⇒ transferable to mcbot:** mcbot 已有 prompt-prefix 缓存，缺的正是**可度量的退化信号**。建议照抄公式与三条豁免
（尤其"服务商从不报缓存"那条，否则本地模型/自建端点会每轮误报）。落地清单：(a) 把任何随世界变的东西从系统提示
搬到 per-turn 信封；(b) 顺手给 mcbot 的 `<inventory>` 类块做对象身份缓存，避免每轮重渲染；
(c) 命中率显示最近一轮而不是累计。**注意**：参考项目的"客户端渲染缓存"前提是它在主人客户端做渲染；
mcbot 身体在服务端，等价的"快照身份缓存"要落在 mcbot 自己那层推送快照上（mcbot 已有 现有的状态推送包 可用）。

## 3. 历史 / 上下文经济学

**压缩触发（信号 / 阈值 / 窗口）**
- 信号 = **上一次请求的 API 实测 prompt token**（`lastPromptTokens`）；后端不报用量时退化为本地估算，
  估算口径全仓唯一一份：**CJK ≈ 1 token/字，ASCII ≈ 4 字符/token，每条消息 +8 token 结构开销**；
  另加**固定开销 8000 token**（系统提示 + 工具表），注释写明"宁可估高提前触发，不可估低撑爆窗口"。
  出处：`EntityAgentLoop.java:1496-1508`、`ai/.../agent/llm/CompactSplit.java:52-76`。
- 触发条件（三条同时）：`contextTokens ≥ window − 13000` **且** 历史 ≥ **8 条消息** **且** 连续失败 < **3** 次。
  出处：`EntityAgentLoop.java:89, 96, 102, 1311-1323`。
- 窗口**逐模型**来自注册表 JSON，缺省回落 **64000**。出处：`ai/.../agent/provider/ProviderRegistry.java:39,166-169`；
  值域示例（`ai/src/main/resources/<provider registry>.json`）：400k / 262144 / 200k / 1M / 2M 多档。
  **注意默认模型回落**：未配置模型时用 `gpt-5.4-mini`（400k 窗口）而非最大窗口——
  出处：`ai/.../agent/llm/the LLM-client class:70-75`。
- 压缩前**先压缩再发本轮**（压缩完 `tryStartTurn()` 重入，在压缩后的历史上派发）。
  出处：`EntityAgentLoop.java:1305-1323, 1471`。

**逐字保留近段（切点规则）**
- 近段预算 **20000 token**（估算口径同上）。从最新往回攒到预算为止，取预算内**最早的**合法切点。
- 保留段第一条**只能是 User（轮边界，首选）或 Assistant（单轮超预算时的劈轮点），永不能是 Tool**——
  "工具结果必须跟着它的调用走，拆开下次请求即 400"。
- 预算内找不到合法切点（一条消息就超预算）→ 保留段为空，退化成全量总结。
  出处：`EntityAgentLoop.java:94`、`CompactSplit.java:8-50`。
- 另有 `preservedTail()`：历史以"无工具调用的最终回复"结尾时，把那一句**额外**逐字跨过压缩边界
  （压缩只在空闲时跑，所以这是常态）。出处：`EntityAgentLoop.java:1474-1489`。
- 切点规则被单测钉死（含"保留段里每个 Tool 的调用都在保留段里"的孤儿检查）：
  `ai/src/test/.../llm/CompactSplitTest.java:51-74`。

**摘要请求的形状**
- 独立系统提示（一句）+ 两步输出引导：先在草稿标签里逐条核对（指令/坐标/物品数量/失败教训），
  再在正式标签里按 7 段固定结构输出（主人指令与意图 / 世界知识坐标 / 自身状态 / 已完成 / 失败与教训 / 待办 / 当前工作与下一步），
  并明令"不调工具、标签之外不输出"。**只保留正式标签**（草稿标签落盘就是白烧 token）。
  出处：`EntityAgentLoop.java:104-137, 1511-1529`。
- 边界先写盘（JSONL 追加一条 compress 事件，带 `preserved` 白名单），再换内存上下文 ⇒ 重放的是压缩后视图，
  压缩前原文留档。出处：`ConvoLog.java:110-132`；`EntityAgentLoop.java:1449-1457`。
- 边界行顺带记账：trigger（auto/manual）、`droppedMessages`、`durationMs`、`preTokens`、`summaryTokens`。
  出处：`EntityAgentLoop.java:1436-1448`。
- **失败熔断 3 次**后不再自动尝试，历史不受影响；压缩被中断按代数戳丢弃；完成后 `lastPromptTokens = 0` 并把缓存诊断 `reset()`。
  出处：`EntityAgentLoop.java:102, 1410-1421, 1459-1461`。
- 手动压缩**不看最少条数门槛**；自动压缩的下限是 8 条（短于这个数不值得动手）。出处：`EntityAgentLoop.java:95-96`。

**会话历史与落盘**
- append-only JSONL，一条一行，带格式版本号与**崩溃安全迁移**（临时文件 + 原子换名，失败保留原文件）。
- **加载软上限 200 条**，且尾部切片要**向前走到最近的 user 消息**（切片以工具结果或半截 assistant 开头会被上游拒）。
- 启动时扫描**未答复的工具调用**并为每条合成"interrupted"结果，否则下次请求 400；尾部悬空 user 消息补一句 assistant。
  出处：`ConvoLog.java:66-69, 265-319`；`EntityAgentLoop.java:329-358`。
- 双视图同源：LLM 视图（压缩后）与显示视图（物理记录），压缩/清空/换人设只渲染成分隔线，不删历史。
  出处：`ConvoLog.java:44-47, 321-356`。

**工具结果进历史前的截断**
- 派发器**日志**里截 200 字符（`ToolDispatcher.java:211-214`）；模型回复日志截 120 字符（`the LLM-client class:255-258`）；
  任务描述进 `<current_task>` 截 **600 字符**（`EntityAgentLoop.java:1584`）。
- **评估器窗口**：总 8000 字符、每行 400 字符（`EntityAgentLoop.java:98-100`）。
- 结果本身对模型的截断由各工具自管，实测cap：范围扫描 **32** 条上限 / 半径上限 **192**、
  实体扫描 **20** 条、配方每查 **4** 个变体、脚手架建议 **12** 种、蓝图按层最多 **24** 层（再多分桶）、
  工具目录一次最多返回 **8** 个定义。出处：`core/.../tools/ScanOps.java:27-28`、`QueryExtraOps.java:46,127`、
  `ScaffoldOps.java:27`、`perception/BlueprintReadTool.java:41`、`agent/FindToolsTool.java:33`。

## 5. 寻路 / 搜索成本

**线程池与线程纪律**
- 共享池，**全部同伴共用一个池**；固定 **max(2, 核数−2)** 线程，**无界队列**，守护线程，
  **最低优先级**，核心线程可超时回收（60s）。理由："A* 是纯 CPU 工作；留两核给服务端 tick 与渲染线程"。
  出处：`core/.../pathing/calc/PathPlannerPool.java:11-54`。
- 每个同伴**至多一个在飞搜索**（重新派发前先轮询 future）⇒ 队列长度实际被同伴数封住。
  出处：同文件注释 :23-25。
- 探针暴露：存活线程 / 活跃线程 / 历史峰值 / 累计完成数。出处：同文件 :61-81。

**未冻结世界视图的执行回退（重要的一条纪律）**
- 若执行上下文声明"不可安全跨线程使用"，搜索**退回提交线程（即 tick 线程）同步执行**
  （返回一个已完成的 future），上下文按用途区分：搜索用上下文冻结，执行用上下文不冻结。
  理由：离线程契约的正确性优先于吞吐。出处：`pathing/bridge/PoolSearchDispatcher.java:39-43`、
  `bridge/ContextFactory.java:59,84`。
- tick 线程只做三件事：构造搜索器（在构造函数里采样世界边界）、提交、**每 tick 轮询一次**句柄
  （poll 幂等，从不 join）。协作取消 = volatile 标志 + 非中断式 future cancel。
  出处：`bridge/SearchHandle.java:15-19`、`AbstractNodeCostSearch.java:62-80, 146-157`。

**启发式档位（不是并行，是同一循环内同时追踪）**
- **7 档系数 `{1.5, 2, 2.5, 3, 4, 5, 10}`**，**在同一个单线程 A\* 循环里顺序推进**（不是 7 个并行搜索），
  每档各自维护"节点估计 + 实际/系数"的最小候选；取用时**按系数从紧到松，取第一个离起点超过 5 格的非空档**；
  七档都不够远 → 判无路。系数 ≥3 的档被采用时打 debug 提示"路径质量可能很差"。
  出处：`core/.../astar/AbstractNodeCostSearch.java:24-37, 154-188`、`astar/AStarPathFinder.java:57-61, 153-162`。
- **anytime 预算切换**：布尔 `failing` 初值为真 → 先用 **failure** 预算；一旦某档候选超过 5 格，改为只用 **primary** 预算。
  出处：`astar/AStarPathFinder.java:68, 158-160`。
- 基础单格成本 `WALK_ONE = 20/4.317 ≈ 4.633`，疾跑 `20/5.612 ≈ 3.564`；启发式权重 **3.563**（≈疾跑乐观值）。
  出处：`pathing/moves/ActionCosts.java:12-30`、`pathing/settings/NavSettings.java:141-142`。
- 最小改进阈值 **0.01**（防浮点噪声反复传播/重堆）。出处：`AbstractNodeCostSearch.java:33-37`。

**节点预算 vs 时间预算（态度很明确）**
- **时间预算是真限制器**：首段 找到半程后 **500 ms** / 毫无结果烧满 **2000 ms**；
  接续段 **4000 / 5000 ms**。出处：`NavSettings.java:153-160`。
- 节点上限 **2,000,000** 只是**失控安全网**，注释三条：
  (a) 实测挖掘寻路约 **5 万节点/秒**，5 秒预算也才 ~25 万，故正常游戏**永不触发**；
  (b) **不许拿它当 CPU 上限**——大复合目标（几十个矿一起搜）超 5 万节点才找到路是常事，
      砍在那里就是"误判无路 → 拉黑近处矿 → 舍近求远"；
  (c) CPU 归线程池与优先级管。命中时返回当前最优半程，与超时同收尾。
  出处：`NavSettings.java:161-171`。
- 主循环**每 64 节点查一次墙钟**（约半毫秒一次），未加载边界触碰次数上限 **50**。
  出处：`astar/AStarPathFinder.java:80-81`、`NavSettings.java:143-144`。
- 节点表初始容量 **1024** / 负载因子 **0.75**；开集二叉堆初始容量 **1024**。出处：`NavSettings.java:149-152`、`astar/BinaryHeapOpenSet.java:13`。

**部分路径接受 / 截尾 / 预计算**
- 部分路径**至少离起点 5 格**才值得采用（`MIN_DIST_PATH`）；否则判无路。出处：`AbstractNodeCostSearch.java:30-31, 159-188`。
- 路径截尾：长度达 **30** 才截，截掉尾部 **10%**（段尾质量差）。出处：`NavSettings.java:177-180`。
- **预计算下一段**：剩余成本低于 **150 tick** 时开始算下一段，并**拼接**进当前路径（`splicePath`）。
  出处：`NavSettings.java:181-184`。
- 已执行路径历史上限 **300**，超限裁掉开头 **50** 步。出处：`NavSettings.java:185-188`。
- 可选"在已加载边界截断路径"（默认关）。出处：`NavSettings.java:175-176`。

**快照 / 缓存 / TTL**

被点名批评的那种"拿节点当 CPU 上限"）；**(b) 7 档系数比单权重更容易同时调和深井与走廊**；
**(c) 250ms 级的部分路径 + 至少 N 格才采用**，避免"起步就返回 1 格路径"的抖动。

## 6. 主线程预算

- **身体自己 tick**：假玩家因为被移出原版客户端区块跟踪（mixin 把 skipPlayer 置真、跟踪视图置 EMPTY），
  原版那套移动/落伤/区块垫全部失效，因此**必须手工重实现**：自己的 `doTick()` 移动通道、
  每 **10 tick** 一次 `resetPosition()+chunkSource.move()`、客户端权威落伤。出处：【perception 子代理报告，
  `entity/the fake-body class` + `mixin/ChunkMapCompanionMixin.java`】——**mcbot 对应的正是这一条：它没有 connection tick**。
- **自过期区块票**：半径 **2** chunk（5×5 垫），票超时 **40 tick**，**每 20 tick 或跨 chunk 时续期**；
  身体一停 tick（休眠/死亡/崩溃）票自然过期 ⇒ **没有显式释放，也就没有泄漏**。多同伴共享一张票。
  出处：同上（`entity/CompanionChunkLoader.java`）。
- **调度器跑在 tick 前段**（`ServerTickEvent.PRE`，先于实体更新）使输入当 tick 生效；
  每 tick 每同伴：重打区块垫 → 背包/效果/载具变更监视 → 唤醒/饥饿/主人受伤轮询 → 任务选择。
- **任务选择是固定 4 级阶梯、无优先级浮点**：本能（10/20/30/50）> 同步槽 > 当前任务 > 空闲姿态。
  出处：【perception 子代理报告】；`api/common/.../task/TaskSelector.java`。
- **本能是"不花 token 的硬编码层"**（架构图明写"本能（硬编码，不花 token）"），
  且**任何本能都可抢占 LLM 任务、完成后归还**。出处：`the mind-model architecture doc:19` 附近。
- 节流常数：右键冷却 **4 tick**、连续破块间隔 **6 tick**、移动超时 **100 tick**、寻路执行重规划守卫见 §5；
  寻路探针的 tick 脉冲以 **50ms** 为健康基准，>60ms 计数、>100ms **抓栈**。
  出处：`NavSettings.java:215-217`、`NavProfiler.java:83-116`。
- **接受陈旧**：寻路读的区块快照最多陈旧 1 tick；方块实体存在性快照同 tick；粗层摘要 TTL 20 tick。

**⇒ transferable to mcbot:** 两件事。（1）**"本能层不花 token"** —— mcbot 若加自动进食/脱困/反杀，
应做成不经过 LLM 的硬编码层并允许抢占，这直接把 token 成本与思考延迟从这些高频场景里去掉。
（2）**自过期票据**优于 mcbot 现在"每拍续票、只续不撤"的写法在异常路径上的表现（mcbot 已是自过期，
保持即可）；mcbot 可补的是"多同伴共享一张票"。
**架构依赖告警**：第 1 条（手工重实现身体 tick + 屏蔽区块跟踪 + 每 10 tick 校正位置）是**假玩家无连接的必然代价**，
mcbot 若还没做"每 N tick 位置校正"，建议对照确认（否则身体可能不被原版跟踪机制正确携带）。
**mcbot 专属**：参考项目把搜索移出主线程；mcbot 搜索在主线程分帧。移池是本节最大收益项。

## 7. 身体 / 动作经济学

**三路受理（单一真源）**
1. **不占身体**（纯查询/UI/登记）→ 不进任务系统，当场回结果；
2. **占身体 + 有界短**（最坏几秒，写得出期限）→ 同步派发，回合挂着等（`runSync`）；
3. **占身体 + 无界**（时长取决于世界）→ 异步派发，**受理即回执** `{task_id, async:true}`（`setTask`），
   身体后台跑，大脑当场自由。
- **"常驻"不是第四条路**：同一异步入口，**给不给数量**决定会不会返终态——给了跑完腾位，不给就永远占着槽。
- 出处：`the mind-model architecture doc:143-149`、§六 :107-141。

**一具身体一件活 + 替换 vs 拒绝的判据**
- 槽里有活时新的异步派发与同步动作**一律拒绝**并报出当前任务号——理由是"排队不可取：串行的工具派发器会被长活整个卡死"。
- 但**替换式受理是常态**：派新活直接顶掉旧活，不要求先叫停。
- **唯一拒绝的情形**：槽里那件是**同一批工具调用里刚受理的**——"那说明模型在一个回合里连派两件活，该让它拿到第一件的结果再决定"。
  ⇒ 这个判据**本地可判**，不必把回合 id 穿到服务端。
- 出处：`the mind-model architecture doc:113-134`。

**避免模型轮询**
- 收尾走**事件**（完成/失败/超时/被叫停都发事件），按队列三态路由（按大脑状态而非事件类型）自动落进"立刻开轮"档。
- **超时事件携带进度**，重派同一调用可续做；`task_status` 拉现场、`task_stop` 叫停。
- **目标重算在任务层、进度携带只在寻路层**：重派 = 从当前世界状态重新求解（背包里已有的收获天然就是进度），
  已算路径由寻路层自己缓存；任务层**永不做挂起/恢复簿记**，因此天然无陈旧状态。
- 出处：`the mind-model architecture doc:116-130`。
- `<current_task>` **由服务端推**（槽一变就发），客户端只照抄不推断——重启/复活重放起来的活，客户端自己看不见。
  出处：`the mind-model architecture doc:123-126`；`EntityAgentLoop.java:1561-1586`。

**收件箱（输入合并）**
- 主人的话与世界事件**共用一条队列**，上限 **200** 条，满了**丢最老并记账**，
  排空时如实补一句"你看到的可能不是全部"。出处：`event/EventQueue.java:34-44, 85-103, 198-201`。
- 成熟度规则只有两条：**有急件 → 熟**；否则看条数（档位 1–10，即"攒够几条"）或**年龄**。
  等待上限随档位拉长：**1 档约 20s、3 档 3 分钟（缺省档 3）、10 档约 33 分钟**。出处：`EventQueue.java:305-328`。
- **躺超 10 分钟的事件标注年龄**（"发生于约 X 前"），跨会话恢复的旧闻尤其要紧。出处：`EventQueue.java:330-340`。
- 排空**只取开头连续一段**（遇到控制条目就停），不插队。出处：`EventQueue.java:203-228`。
- 倒箱拼成**一条**用户消息，固定顺序：状态快照 → 事件（`<events>`）→ 主人的话压轴。出处：`EventQueue.java:159-196`。
- **急件叫醒"脉冲可丢、电平不骗"**：只通知"来问吧"，不递事件；正确性从不依赖叫醒。出处：`EventQueue.java:23-33`。

**计时器**
- `set_timer` 不占身体、不进任务槽、当场返回；记**主世界游戏刻绝对值**（世界不跑表就不走、重启不重新计时）；
  上限 **每同伴 8 个**，秒数范围 **1–1200**，**每 20 tick 扫一遍**。
  出处：`task/TimerRegistry.java:54-62`、`task/SetTimerTool.java:29`。
- **"禁止轮询"只有提示词级与回执措辞级的强制，没有运行时冷却**：
  一个反复调 `task_status` 的模型不会被任何东西挡住。⇒ 这是**已知缺口**，不是可借鉴的优点。
  出处：`the static-prompt class:58-63`、`task/TaskDispatch.java:90-106`、`tools/work/AutoMineTool.java:39`。
- **被替换的活一定会被结算**：旧记录被标 `REPLACED` → `CANCELLED` 并结算，因此它的 `tool_call` 总能拿到结果——
  否则对话里会留下一个永远没有结果的工具调用（下次请求 400）。
  出处：`task/TaskSlot.java:68-85`。
- **拒绝话术按"常驻 / 有界 / 外接脑"三分支**：常驻说"它永远不会发 task_finished，直接派新活就是停它的方式"；
  外接调用说"用 `task_status` 查"；内脑说有界活"别轮询，task_finished 会来"。
  出处：`task/TaskDispatch.java:90-106`。
- **网络包体积硬上限**（防一次调用把桥撑爆）：工具调用 id **128**、工具名 **128**、
  参数 JSON **16 KiB**、结果 JSON **16 KiB**。出处：`network/.../payload/ExecuteToolPayload.java:62-64`、
  `network/.../payload/TaskResultPayload.java:35-36`。⇒ **mcbot 的桥 body ≤64KB 可以直接照这个拆细**。
- 主人打断：**代数戳自增**，在飞响应落地即弃；每个未决工具调用合成"cancelled"结果保住协议；
  排队中的指令类条目按类型表清掉、事实类保留。出处：`EntityAgentLoop.java:846-906`、`event/EventTypes.java:66-90`。

**目标经济**
- 轮数硬上限 **30**、目标正文截 **4000 字符**、**连续 2 次判"原地打转"即收工**；
  判"打转"的是**评估器**，不是它自报（"她报不准，前面验过"）。出处：`GoalState.java:34-38, 80-96`。
- 四种终止（达成/打转/跑满轮数/主人喊停）**结果都是清掉**，刻意不留"暂停中的目标"。
- `hand pin` 宽限 **600 tick**、任务推送间隔 **20 tick**。出处：`task/CompanionBrain.java:39, 63`。

**⇒ transferable to mcbot:** 这是 R2-S4 最成熟的一份形态，且**判据全部本地可判**。建议整体搬走：
(a) 三路受理 + "常驻不是第四条路"；(b) **"同一批里的第二件才拒绝"** 这条精确判据（mcbot 派发器可本地判）；
(c) 收尾走事件顶替最后一次往返（mcbot 已有 `AgentRunner`/桥事件，可直接接）；
(d) 替换式受理 + 注入 `<current_task>` 时**明确说"直接派新活顶掉旧活"**（不说会白白多一轮 stop）；
(e) 任务层不做挂起/恢复簿记，重派即重算。收件箱的**档位化成熟度 + 年龄标注 + 丢弃记账 + 倒箱拼一条消息**也建议照抄。
**架构依赖**：mcbot 的"当前任务镜像由服务端推"这一条天然契合（身体在服务端），可直接做；
"同一批第二件拒绝"需要 mcbot 派发器持有本批调用清单（早期派发下，需按响应序号界定"批"边界）。

## 8. 度量与仪表（实测记录什么 / 拿什么当回归门）

**逐调用（INFO，一行）**：耗时 ms、SSE 块数、token（in/out/total）、结束原因、工具名列表、正文片段（截 120 字符）。
出处：`the LLM-client class:215-236`。
- 每次调用有短序号请求 id（`lr-N`），贯穿"发送 / 响应状态 / 每一块"的日志行——多同伴并发时唯一能对账的东西。
  出处：`HttpLlmTransport.java:37-41`。
- 请求开头的 debug 行同时给出 `msgs`、`tools` 数量、**`system_prompt_chars`**（缓存前缀体量的直接观测）。
  出处：`the LLM-client class:192-196`。

**逐回合（INFO）**：`convo=N msgs, tools=M`（开轮时）。出处：`EntityAgentLoop.java:1334-1335`。
- `runtime_state` 全文以 debug 打印（"她看到的世界"平时不可见，靠它抓过"任务完成事件与镜像在同一条请求里打架"）。
  出处：`EntityAgentLoop.java:1551-1557`。
- 背包块进请求时打：**字符数 + 这份快照是多少 ms 前收到的**——且只在快照真换了时才打，
  因此这行读的是"背包这段时间没变过"，不是延迟；**该行不出现才是链路断了**。出处：`EntityAgentLoop.java:1619-1622`。
- 工具派发/结果各一行 INFO，含排队深度（`queued=N`）。出处：`ToolDispatcher.java:182-183, 204-205`。

**逐会话（持久化）**
- `TokenLedger`：四元累计 + 新处理总量，落盘每回合一写（文件极小）；
  **命中率与缓存诊断不落盘**（前者只看最近一轮、后者只本次运行）。出处：`client/.../agent/TokenLedger.java:16-23, 77-97`。
- **读出口的阈值**：`/usage` 面板给最近一轮命中率上色，**≥ 0.7 判 GOOD，否则 WARN**；
  并单独一行报"缓存重付了 N token，M 次"。⇒ **这是把诊断指标变成人可判读信号的那一步**，
  也是本仓唯一一处为效率指标写死的判读阈值。出处：`client/.../command/UsageCommand.java:77-93`。
  命中率在屏显的另一处也被消费：`client/.../screen/the main panel screen class:1271`。
- 压缩边界行携带 `preTokens` / `summaryTokens` / `droppedMessages` / `durationMs`，作为**跨会话的成本历史**。
  出处：`EntityAgentLoop.java:1436-1448`。

**寻路探针（默认关，开关一开即 5 秒一窗口 INFO）**
- 窗口长度 **5000 ms**；行内含：`navTicks`（含 /s）、每个阶段的 次数 / 总 ms / 均 µs / 峰 ms
  （插桩相位为**目标编译**与**核心 tick** 两处）、后台搜索 次数/总 ms/峰 ms、线程池 线程/活跃/峰值/完成增量、
  GC 次数与停顿 ms（**占窗口百分比**）、服务端 tick 间隔 `gapMax` + `over60` + `over100` 计数。
- **"总 CPU 时间可以远超窗口墙钟"这一点被写进代码注释**（后台搜索并行跑在多核上）——
  否则读日志的人会把 5 秒窗口里的 8 秒 CPU 当成测量错误。
- **健康基准写在代码里：tick 间隔 ~50ms 为顺；>60ms 计数；>100ms 抓栈**；间隔 ≥2000ms 视为任务空档不计。
- **卡顿抓栈**：后台采样线程每 **25 ms** 抓一次服务端主线程栈进 **64 槽环形缓冲**（≈1.6s 现场窗口），
  压缩到最多 10 帧，tick 间隔超 100ms 就打出来（最多 3 个不同栈）——**覆盖所有计时相位之外的盲区**
  （光照、区块 I/O、别的 mod）。
- **没有 nodes/s 计数器**。"约 5 万节点/秒"只作为节点上限注释里的数量级论证存在，
  真正的节点数字只出现在**开启探针时的每次搜索收尾行**（停止原因 / nodes / maxNodes / failing / 目标）。
- 出处：`core/.../pathing/util/NavProfiler.java:20-33, 83-127, 195-276`、`astar/AStarPathFinder.java:169-180`。

**回归门**
- 官方 CI（`the CI build workflow`）**只回答"能不能编译 + 纯 JVM 测试"**，
  没有任何性能阈值门；性能靠上述探针人工判读 + 重构日志逐条记账（`the pathing design log`）。
  ⇒ **【不确定】性能回归门在本仓没有自动化形式**；可借的是"指标本身 + 健康基准"。
- 代码里真正被断言钉住的是**正确性**而非性能：缓存诊断 7 个用例（含豁免规则）、
  压缩切点 5 个用例（含孤儿工具结果检查）、用量归一 10 个用例。
  出处：`CacheWasteTest.java`、`CompactSplitTest.java`、`UsageAccountingTest.java`。

**⇒ transferable to mcbot:** mcbot 的验收纪律是"证据（时间戳+日志判读）进 STATUS"，正缺一份**可复跑的性能哨兵**。
建议照搬三件：(a) **`gapMax / over60 / over100` 三计数 + 超 100ms 抓主线程栈的环形缓冲**——
这是"服务端卡还是客户端卡"的决定性信号，且实现代价极小；(b) **5 秒窗口分阶段 次数/总/均/峰** 的汇总行；
(c) **`system_prompt_chars` + 缓存漏计** 双指标一起进日志（前者定位是谁动了前缀，后者量化代价）。
**mcbot 专属**：mcbot 的"每 tick ≤300 节点"应当直接进这份哨兵作为被监控量；
其 `SelfTest` 无头 harness 适合作为这些计数的自动断言载体（比参考项目的"只测正确性"更进一步）。

| 全局每 tick 搜索配额 | 128 检查 + 256 群系采样 + 256 段扫描 + **4ms** 硬墙钟（所有同伴共享） | 单一主线程预算口，跨工具统一 |
| 方块扫描 | 半径 ≤192，结果 ≤32，死线 600 tick，收集 ≤8192 | 无界扫描不可能发生 |
| 目标索引饱和/驱逐 | 每目标每段 256 / 每 200 tick 扫 | 内存有界且查询便宜 |
| 寻路线程池 | max(2, 核数−2)，无界队列，守护，最低优先级 | 共享池，多同伴不涨线程；给 tick/渲染留两核 |
| 未冻结视图回退 | 不可安全跨线程 → **退回 tick 线程同步跑** | 离线程契约的正确性优先于吞吐；平台不支持时性能自动降级而不是出错 |
| 启发式档位 | 7 档 {1.5,2,2.5,3,4,5,10}，**同一循环内**逐档追踪最优候选 | 同时服务深井与走廊；比单权重更稳，且不付并行搜索的代价 |
| anytime 预算切换 | 某档候选 >5 格后由 failure 预算切到 primary 预算 | 有半程就用短预算收工，避免为"更优解"多烧 1.5s |
| 部分路径最小距离 | 5 格 | 避免"起步就还你 1 格"的抖动 |
| 搜索时间预算 | 首段 500/2000 ms，接续段 4000/5000 ms | **真限制器**；分数毫秒级响应 |
| 节点上限 | 2,000,000（安全网） | 正常永不触发；**禁止当 CPU 上限**（会误判无路→拉黑近处矿） |
| 墙钟检查间隔 | 每 64 节点 | ~0.5ms 粒度，超时及时 |
| 未加载边界触碰上限 | 50 | 探路不把服务端拖在区块生成上 |
| 路径截尾 | 长度 ≥30 截掉尾 10% | 砍掉段尾低质动作 |
| 预计算下一段 | 剩余 <150 tick | 消除"走走停停" |
| 区块快照 | 半径 8 chunk，每 tick 整体重建，无失效追踪，空闲 600 tick 释放 | 陈旧 ≤1 tick，零失效追踪成本 |
| 导航视图缓存 | **只有"上一个区块"一个指针**，无逐格 memo | 逐格哈希表曾膨胀到数百万条并引发 GC 停顿——这是被实测否决的设计 |
| 粗层/分层规划 | **文档有、代码无**（不存在 hier 包与 COARSE_* 常量） | 该层的一切参数不可当事实；其设计目标当前由"接续段预算 + 预计算 + 拼接"承担 |
| 命中率判读阈值 | 最近一轮 ≥0.7 判良好 / 否则告警 | 把诊断指标变成人可判读的信号（唯一写死的效率阈值） |
| 重规划放弃 | 硬保险丝 200，连续卡住 6，进步阈值 4.0 | 真围死才放弃，不误杀 |
| 活目标刷新 | 每 5 tick；目标移动 >2 格重根 | 躲的是"现在的怪"而不是几秒前的坐标 |
| 执行期复核 | 向前 5 步；涨价 >10 中止；movement 超 100 tick 判卡 | 快照错误在下一步就被抓到 |
| 区块票 | 半径 2（5×5），40 tick 超时，每 20 tick 或跨 chunk 续 | 自过期，无显式释放即无泄漏 |
| 输入队列 | 上限 200，丢最老并记账 | 消费者长期不来也不撑爆上下文 |
| 成熟度档位 | 1–10（缺省 3）；等待上限 `60s×档²/3`（3 档=3 分钟，10 档≈33 分钟） | 既能攒批省轮次，又不会退化成永久沉默 |
| 事件年龄标注 | 躺 >10 分钟 | 跨会话旧闻不会被当成刚发生 |
| 计时器 | 每同伴 8 个，1–1200s，每 20 tick 扫 | 不占身体、当场返回，替代轮询 |
| 目标打转判定 | 连续 2 次（评估器判，非自报） | 早停，省掉"绕二十轮" |
| 探针窗口 / 抓栈 | 5000 ms 窗口；25ms 采样 × 64 槽环形；>60ms 计数、>100ms 抓栈 | 直接指认主线程堵在哪个方法；区分服务端卡/客户端卡 |
| 健康 tick 基准 | gapMax ≈50ms | 写进代码的判读依据，不是感觉 |

| 无路判定 | 目标图不完整时最多连续 40 次失败才拉黑；图完整立即拉黑 | 防"误判无路 → 拉黑近处矿 → 舍近求远" |

| 执行期集合重建 | 只重建 当前位置 ±10 movement 的窗口 | 每 tick 复核但不整表重算 |

### 三条最贵的建议（若只做三件事）
1. **把 mcbot 的 A* 移出主线程**（有界池 + 冻结/只读快照 + 时间预算），撤掉"每 tick ≤300 节点"这个
   **被参考项目点名批评的"拿节点当 CPU 上限"**形态。这是单任务墙钟最大的一笔。
2. **加缓存浪费诊断 + `system_prompt_chars` 双指标**，并把所有随世界变的东西赶出系统提示。
   机制便宜、收益持续，且能防住"某天有人往系统提示塞了个会变的字段"这类静默退化。
3. **建一份可复跑的主线程性能哨兵**（gapMax/over60/over100 + 超阈值抓栈 + 5 秒分阶段汇总），
   接进 mcbot 的 `SelfTest`，让"没卡崩"从人工判读变成自动断言。

## 依赖告警（mcbot 没有 connection tick，以下机制**不能照搬形态**）

参考项目的许多"省事"来自一个前提：**身体所在的客户端有一条每 tick 的心跳通道**，
以及**服务端有一条 tick 循环**。mcbot 的假玩家没有 connection tick，桥/循环的驱动方式不同。
逐条列出**依赖点**与**mcbot 应该怎么办**：

| 参考项目的机制 | 它依赖什么 | mcbot 的对策 |
|---|---|---|
| 15 分钟工具兜底（`ToolDispatcher.tick()`） | **客户端 tick**（`AgentLoopRegistry.tickAll()`） | mcbot 有 `AgentRunner.tick()` 在客户端主线程做超时巡检（`ARCHITECTURE.md` §2 已列）⇒ **可用同一形态，但要确认兜底时长与"桥断线"叠加后的行为** |
| 队列"条数/时长"成熟度自动排空 | 同一条客户端 tick | 急件在 push 时直接叫醒，不受影响；**非急件的按龄排空在 mcbot 需要自己的 tick 或定时器** |
| 计时器到期 | **服务端 tick 循环** | mcbot 已有 `CompanionScheduler`（`END_SERVER_TICK`）⇒ 可直接承载 |
| 饥饿/受伤/醒来/复活/区块垫刷新 | 服务端 tick 循环 | 同上；mcbot 的身体在服务端，这块**比参考项目更直接** |
| 背包/效果/载具状态进入请求 | **服务端推快照** | mcbot 已有 现有的状态推送包 推送路径 ⇒ 形态一致，可直接做"身份缓存 + 变更才推" |
| 身体自己 tick 的移动通道 / 每 10 tick 位置校正 / 落伤自算 | 手工补偿无连接的身体 | **mcbot 必须自己确认这三件**（`ARCHITECTURE.md` 已记"挖掘手工计时引擎"，移动/位置校正需逐项核对） |
| 粗层/分层规划器（48 格阈值、距离场、封死判定） | **代码里不存在**（只有设计文档） | 不要按文档实现；先用"接续段预算 + 预计算 + 拼接"拿到大部分收益 |
| 每 tick ±8 chunk 快照 | 与它的票据半径耦合 | mcbot 票据半径是 2 ⇒ 快照半径要重定，不要照抄 8 |

**另有两处"看起来能抄、实际要当心"**：
- **"禁止轮询"只有提示词强制，没有运行时冷却**：参考项目自己也没有防住反复 `task_status` 的模型。
  mcbot 若要做，得自己加一个真正的每任务查询冷却（本轮勘察未发现参考项目有此机制）。
- **`parallel_tool_calls` 被请求为真，但身体严格串行**：批量是"请求侧"的收益，
  不要误以为可以在身体上并发执行（一具身体一件活是硬约束）。
