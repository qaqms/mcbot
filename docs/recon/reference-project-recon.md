## 1. 总体架构

### 1.1 模块切分（Gradle 多子工程，单一构建）

- `ai/`：纯 JVM、零 Minecraft 依赖的"大脑—服务商连接层"。住户：HTTP/SSE 传输、提示词文本、线格式适配（含站点注册表）、客户端会话/会话日志。这是最值得 mcbot 对照的一层：它把"模型通信"与"世界"物理隔离，因此可以脱离游戏跑单测。
- `api/common|fabric|neoforge`：引擎（服务端假玩家本体 + 大脑调度 + 工具契约 + 事件 + 网络包 + 客户端 agent 循环 + MCP 服务端/客户端 + 客户端 UI 入口）。README 自述该模块曾是独立仓、现为同仓子工程。
- `core/common|fabric|neoforge`：内容层（约 30 个工具、寻路引擎、任务执行器、技能 Markdown、游戏内测试结构）。
- `ui/`：纯客户端 UI 工具箱（widget、文本换行、动画、主题），无 Minecraft 之外的依赖，配无头单测。
- `plugins/ysm`、`plugins/tlm`：第三方模组联动包，各自独立发布。
- 治理原则明文写在 `docs/architecture-mind-model.md`：**"机器进 api，内容进 core"**，第三方内容包与 core 地位平等，只能从四个登记口插入（任务链、任务执行器工厂、工具注册表、本能名册）。

**Why it matters for mcbot:** mcbot 的桥/工具/感知若能与游戏解耦（至少是"可无头测试"级别），R3 的面板迭代与 M5 的网格算法才不会被启动服务端的成本拖住；参考项目 `ai/` 与 `ui/` 两个模块的存在本身就是这条纪律的证据。

### 1.2 LLM 调用住在哪

- 内置大脑**整体在主人客户端**：每只同伴一个 agent 循环实例，按实体稳定 UUID 索引（不用会话内 int 网络 id，因此穿维度重建实体后循环与对话仍然健在）。API key 只在客户端配置里，服务端不接触。
- 服务端只负责"身体"与"任务执行"：客户端把工具调用打成自定义包发服务端，服务端校验后执行，结果打成另一个包回来。
- 另有一条**反向**通道：本机可起一个 MCP 服务端（JSON-RPC 2.0 over JDK HttpServer，`/mcp` 一个端点），让外部 AI 客户端（Claude Desktop / Cursor 等）接管同伴。开启期间内置大脑完全不发请求（"一具身体一个脑"硬闸），主人的游戏内发言改由事件线交给外部脑。
- LLM 传输零第三方依赖：JDK `HttpClient` + Gson。支持两种线协议：OpenAI 兼容（绝大多数站点）与 Anthropic Messages 原生协议，站点/模型清单外置为 JSON 资源（首次运行复制到用户配置目录供改写）。

**Why it matters for mcbot:** mcbot 已是"服务端假玩家 + 主人客户端 agent 循环"，与此同构；可直接借鉴的是**按稳定 UUID 而非会话内 id 索引循环**（跨维度/重连不丢对话），以及**外部脑接管时内置脑硬停**这一条单一真源式闸门。

### 1.3 agent 循环结构与线程纪律

- 每同伴一个循环对象（单层，不做"玩家级 agent + 实体级 agent"两级；文档明确记载两级设计曾因调试困难被回滚）。循环只管会话与回合；工具执行被抽出到独立的**派发器**，后者是**严格串行队列**（上一件结果落地才派下一件），一件超时兜底存在但极其宽松（分钟级）。
- 线程规则：所有状态变更在主线程；LLM 响应在 HTTP 线程完成后 bounce 回主线程；工具结果可能来自任意线程，靠统一提交口回主线程。回合代数戳（generation）用于丢弃"被打断后才落地的旧响应"。
- 大脑**不在 tick 循环里**：只在三个时刻运转——主人说话、外部消费者显式唤醒、自己的工具结果回来。身体层则是每 tick 一次"竞价"：所有想控制身体的机制投标（本能优先级高、LLM 任务优先级最低，任何本能都可抢占并在完成后归还）。
- 模型输入分四层：A 静态框架（系统提示 + 工具表，每回合现场组装）、B 历史（含压缩摘要）、C 本回合新输入（主人消息 + 排队事件）、D 回合内回填（工具结果）。**动态注入口只有两个**（C 的事件、D 的工具结果），并明确"哪个注入口能塞什么"是宪法级约束。

**Why it matters for mcbot:** "本能可抢占 LLM 任务、完事归还"是一个干净的多机制共存模型——mcbot 若将来加入自动进食/脱困/反杀，不必把它们塞进 LLM 循环；而"大脑不在 tick 循环"能让 R3 的 UI 与心跳逻辑保持轻。

### 1.4 与模型对话的方式（这是 R2-S3 的直接参照）

- **流式是默认**：请求开 SSE 并索取用量帧；每收到一块交给 provider 的增量累加器，最终由累加器产出完整助手回合（文本 + 工具调用 + 思考流 + 保留的非标准字段）。
- **但被派发的工具调用仍是"整条流结束之后"一次性拿到**：流内的分片只用于 UI/语音/思考泡的实时呈现（内容增量与推理增量分别喂给不同的 UI 流），工具调用不提前派发。
- 回合内**不限制工具回合数**，也没有循环守卫（文档理由：能干的 agent 会合法地串很长；失控由主人中断叫停，长期目标另有一道 30 轮保险丝）。
- 请求级可观测性：每次调用有一个短序号 id，贯穿"发送 / 响应状态 / 每一块"的日志行；一轮收尾打一行摘要（耗时、块数、token 用量、结束原因、工具名列表、正文片段）。

**Why it matters for mcbot:** 参考项目已经把"流式"做成了默认与既有能力，**但恰好没做 R2-S3 的"提前派发"**——它的做法说明了提前派发的两个前提：(a) provider 侧必须能把"工具名/参数增量"从流里增量解析出来（它有专门的增量累加器，这是现成的参照位）；(b) 需要一份"半截调用能否安全先行"的策略，因为工具一旦开跑就会有副作用。mcbot 该做而它没做的是：**在首个工具调用参数完整闭合时即派发，并让后续到达的文本继续流入 UI**。

## 2. 感知 / 世界表征（M5 直接相关）

### 2.1 机制（`look_around` 工具）

- 形状：**自我中心俯视字符网格**，一格 = 一方块，`@` 居中，北在上、东在右；默认半径 8（17×17），可选半径 4–16。
- 每格不是方块 id，而是**语义池化后的"移动可达性符号"**：平地 / 上一级台阶 / 下 1–2 格 / 坠落 ≥3 / 墙 / 水 / 岩浆危险 / 危险缓冲 / 树 / 未加载，共 10 类。竖直信息被"塌"成一个符号。
- 判定与寻路**同一把尺**：每格用寻路的可站立/可穿行/岩浆谓词真算，中心点取寻路口径的"玩家脚位"，因此网格与路径规划的世界观不会互相打架。
- 危险格做**一圈膨胀**（岩浆邻格标成"小心"），照抄自动驾驶 costmap 的 inflation 思路，让模型天然远离岩浆边缘。
- 未加载的列直接标"未加载"，读取走**只读已加载视图**（只查内存中的区块，绝不触发同步加载或生成）。
- 输出是纯文本块：首行给出中心坐标 + 朝向 + 方向约定，随后是网格，末尾是图例 + "逐格描路"的路由提示（鼓励模型在网格上做 Visualization-of-Thought 式推理）。
- 分工明确：**近场稠密几何用网格，远处稀疏对象（矿/箱/怪）交给既有的方块扫描与实体扫描工具**。

### 2.2 体积与成本控制

- 首行 + size² 格 + 空格分隔 + 两行图例；半径 8 即 289 格。文档明确把"省 token"当作设计目标之一。
- 竖直方向只在脚位 ±一个小带宽内探测（向上 1 格、向下 3 格）就足以区分"可走/可跳/可下/坠落/墙"。
- 后续 TODO 明确列出但**暂缓**的增强：近细远粗的多分辨率网格（远处聚合）与第二层水平切片。理由写得很清楚：**高度图被明确否决**（表达不了悬挑与头顶净空），稠密体素太重。

### 2.3 设计依据（文档自述的调研结论，值得只读参考）

- 引用的外部研究结论：以 agent 为中心的语义字符矩阵，显著优于"坐标元组列表"与"原始俯视图"，且消融显示"网格格式本身"是主要增益来源；另有"让模型自己画 ASCII 网格追踪空间状态"的推理方法。
- 明确对比了若干 Minecraft LLM 项目：它们普遍只喂"去重方块名集合"或"相对身体部位标签"，把空间推理外包给寻路器——也就是**没有真正的空间地图**。触发此项设计的实测现象是：单次任务里出现数十次单格探测（`inspect_block`），因为模型"看不见"。

**Why it matters for mcbot:** M5 的字符网格可以完全按上述参数起步（1 格 = 1 方块、半径 8、10 类移动性符号、危险膨胀、未加载标 `?`、与寻路共用谓词），并以"回合内单格探测次数下降"为验收指标；参考项目已经替 mcbot 试过并否决了两条路（高度图、稠密体素），照做即可省下两轮返工。

## 3. 动作 / 工具层

### 3.1 原子动作清单（约 30 个，按族）

- **感知/查询**：空间网格、范围方块扫描、范围实体扫描、自身状态（HP/坐标/装备/整包）、主人状态、世界信息、单格探测（方块属性、硬度、所需工具、预估挖掘刻数、是否在触及距离内）、读取机器内容（物品/流体/能量，不打开界面）、脚手架材料、蓝图读取。
- **移动/工作（异步长活）**：寻路前往（可指定"到达语义"）、跟随、挖掘（自动换工具）、采集掉落物、攻击、钓鱼、按蓝图建造、建造结构、大范围钻取。
- **物品/容器**：合成、查看配方（跨全部配方类型并标出所属工作台种类）、穿戴/卸下、吃、丢、取物、物品转移。
- **交互**：对坐标交互、对实体交互、开着的界面探测、关界面、睡觉。
- **定位**：定位结构、定位生物群系。
- **agent 自用（默认不暴露给外部脑）**：结构化待办清单、技能加载、工具目录检索。

### 3.2 多步计划的表示与执行

- 计划**不是**引擎内部的数据结构，而是交给模型自己维护的**结构化待办清单**（内容/状态/优先级三元组，每次调用整体替换），并以卡片形式在 UI 侧栏显示；提示词规定"3 步以上才写、完成一步才前进一项、不要在意图或派发时就标完成"。
- 引擎侧只有"当前任务槽 + 一笔活"的表示，没有计划解释器——计划与执行解耦。
- 另有**技能（Skill）**机制：一层层目录里的 Markdown（含插件 jar 内的），按"就近覆盖"合并，系统提示里只列摘要，模型按需"加载技能"把正文取进上下文。技能是"怎么玩这个模组"的说明书，与工具正交。

**Why it matters for mcbot:** mcbot 若想加"多步计划"表示，最省的路是照此做"模型自维护清单 + 只影响提示与 UI"，而不是在引擎里造计划机；技能 Markdown 是低成本扩知识的抓手（比扩提示词或加工具都便宜）。

### 3.3 长动作的处理：受理即回执（R2-S4 的直接参照）

- 受理判据是明确的**单一真源**，工具作者三选一：
  1. **不占身体**（纯查询/UI/登记类）→ 不进任务系统，当场回结果；
  2. **占身体 + 有界短**（最坏几秒，写得出不冤枉它的期限）→ 同步派发，回合挂着等；
  3. **占身体 + 无界**（时长取决于世界：路程/资源/敌人）→ 异步派发，**受理即回执** `{task_id, tool, async:true, standing}`，身体后台跑，大脑当场自由（可继续聊天、感知、规划）。
- **常驻不算第四条路**：同一个异步派发入口，"给不给数量"决定任务会不会返终态——给了就跑完腾位，不给就永远占着槽。工具作者写一次逻辑，两种用法白送。
- **一具身体一件活**：车道上有活时，新的异步派发与同步动作一律给出**拒绝回执**并报出当前任务号；**替换式受理**是常态（派新活顶掉旧活，不要求先叫停），唯一拒绝的情形是"同一批工具调用里刚受理的那件"（说明模型一回合连派两件，该先拿到第一件结果）。
- **收尾走事件不走工具结果**：完成/失败/超时/被叫停都发事件，按队列三态路由（见 §7）；超时事件**携带进度**，重派同一调用可续做；`task_status` 拉现场，`task_stop` 叫停；**明确禁止轮询**。
- 客户端每个用户回合注入一份 `<current_task>`，内容由**服务端推**（槽一变就发），客户端只照抄不推断（重启/复活重放起来的活，客户端自己是看不见的）。
- **目标重算在任务层、进度携带只在寻路层**：重派任务 = 从当前世界状态重新求解（背包里已有的收获天然就是进度），已算路径由寻路层自己缓存；任务层永不做挂起/恢复簿记，因此天然无陈旧状态。
- **改地形的授权**：默认路径不动世界。当"不动地形的路找不到"时，引擎不立刻终局，而是用"允许改地形"的上下文**只搜不走**地探一次，把那条路会挖什么、放什么列成清单（按方块种类分组、点名坐标）交给模型，由模型决定要不要带授权参数重派。裁决权在模型，引擎不替它猜"这是不是玩家的房子"。
- 任务结果结构含：成功与否、是否超时、人话消息、结构化数据（如终点坐标）；文档强调"成功"不是单一问题（e.g. 走到了但没到位）。

**Why it matters for mcbot:** R2-S4 需要的一切在这里都有可对照的成熟形态：回执字段（任务号/是否常驻）、"同一批第二个调用拒绝"的判据（**本地可判**，不必把回合 id 穿到服务端）、收尾改走事件以抵消"最后那次工具往返"的开销、以及"拒绝话术把选择权丢回模型"。另外"引擎只搜不走地探一次 + 交清单给模型授权"是处理破坏性路径的漂亮解法，比硬编码白名单更耐模组。

### 3.4 失败要教人（贯穿性设计）

- 工具返回被要求写成**"为什么失败 + 通常的下一步"**（例如"徒手挖不了铁矿——至少装备石镐"），失败也是知识注入通道；提示词明确规定"失败结果会教你，照着改，不要原样重发"。
- 参数校验失败、未知工具、未取回参数定义的工具被调用，都返回**教学式**错误（先错在哪，再怎么办）。

**Why it matters for mcbot:** mcbot 已有 status/scan 等工具；把"失败文案"当一等公民（含纠错指引与建议坐标）能显著降低无谓往返，这是纯 prompt 工程收益。

## 4. 寻路 / 导航

### 4.1 算法与并行

- **加权 A***（成本单位 = tick，由真实物理耗时换算；坠落成本表由逐 tick 重力模拟生成），扩展自经典开源寻路架构的路子（**该仓无任何第三方版权头，属自写实现**；其文档在若干处点名对照过开源机器人寻路器的行为与阈值）。
- 同时跑 **7 档启发式松紧系数**（从接近最优到激进扑向目标），各自保留最优候选；时间预算耗尽时取可用的部分路径，实际是一个**随时可中断的 anytime 搜索**。
- 搜索在**共享线程池**上跑（线程数 = max(2, 核数-2)，无界队列，守护线程 + 最低优先级）；若计算上下文不是冻结快照，则**退回主线程同步跑**（宁可慢也不并发读活世界）。
- 执行仍在服务端 tick 线程：逐 tick 复核成本、走原版物理输入。
- 有性能探针（线程池快照、分窗口日志）与寻路调试渲染通道。

**Why it matters for mcbot:** 若 mcbot 的 A* 目前在主线程，参考项目给出了一个低风险迁移形态：**有界池 + 守护低优先级线程 + 未冻结则退回主线程**、"搜索在 worker、执行在 tick"分离。7 档系数是低成本的路径质量/响应速度折中（比单一权重更容易调和"深井"与"走廊"两类场景）。

### 4.2 未加载区块

- 每 tick 重建一份"同伴周边已加载区块"的**只读快照**（仅收集活区块引用，用非阻塞查询，不触发加载/生成）；worker 读快照。因为每 tick 重建且之后不再改，**不存在缓存失效追踪、也不存在超过一 tick 的陈旧**。
- 执行期与感知期走"只读已加载视图"：未加载一律当空气/空流体，**绝不触发同步生成**——避免把服务端线程卡在生成区块上。
- 路径可以越过区块边界，但有**触碰未加载边界的次数上限**；未加载处估出的移动原语在加载后若涨价超过阈值即中止该段。
- 可选用"在已加载边界截断路径"。

**Why it matters for mcbot:** 这是"假玩家远离主人自主干活"的核心保障，且实现代价很低（一次 gather + 每 tick 重建）。mcbot 已有 chunk-ticket 管理，可对照其**快照 + 只读视图 + 边界触碰上限**三件套补齐"探路不卡服"。

### 4.3 分层粗图（长途加速 + "封死"判定）

- 只对**目标距离 > 48 格**的长途启用；短途维持零开销。
- 把世界按 16³ 段采样：每段算 6 个面的三态摘要（有 2 高可穿行格 / 有可破坏材质 / 整面硬），纯空气/纯实心段走 O(1) 均质快路径。
- 从目标侧做一次**多源 Dijkstra** 得到"段 → 下界代价"的距离场，作为 A* 启发式的**有界引导**（公式上对原启发式做上限截断）。
- 语义决策（文档明确写"动之前必读"）：
  - 摘要是**地形性质**，能力在查询时施加；
  - 距离场是**有界、故意不可采纳**的引导，**不是正确性来源**——正确性由细搜索 + 执行复核兜底；
  - "封死"判定必须**保守**：只有前沿被真正耗尽（而非预算截断）+ 沿途全脸扫描过 + 全在快照内才下结论，任何采样不足/超限/快照外一律返回"未知"，照常细搜索。理由：**误报"封死"会导致错误拉黑，宁可漏报不可误报**；
  - 场在派发时构建（tick 线程，读该次搜索同一快照），搜索期间冻结；摘要缓存 TTL 约 1 秒。
- 收益：走廊直奔、深井不再烧预算乱探、封死洞穴秒报（省掉整个失败预算）。

**Why it matters for mcbot:** 若 mcbot 的挖矿/长途偶发"烧满预算"，这条"粗层只作引导 + 保守封死 + TTL 缓存"是可直接借鉴的形态；尤其"不可采纳启发式 + 细搜索兜底"的分工，比试图让粗层给出精确答案更稳。

### 4.4 重规划、预算与放弃判据

- 失败由状态机自动重搜；**放弃判据住在任务过程层**：连续 6 次失败重规划且目标启发值无实质改善（阈值约"前进一格"的尺度）→ 判"被围死"；另有 200 次硬保险丝（理性上限，不是真放弃条件）。
- 活目标（如"远离那几只怪"）每 5 tick 重取一次目标，让威胁坐标快照跟上（否则躲的是几秒前怪站过的位置）。
- 目标中心移动超过 2 格即重根。
- 分首段/接续段两套时间预算（找到可用部分路径后的预算 vs 毫无结果时烧满的预算），执行期在剩余成本低于阈值时**预计算下一段**并无缝接上。
- 有"节点数安全网"，但文档明确**禁止拿它当 CPU 上限**：正常由时间预算约束，砍节点会造成"误判无路 → 拉黑近处矿 → 舍近求远"。

**Why it matters for mcbot:** "拉黑近处矿"这类副作用正是节点/时间预算设计不当的典型症状；参考项目的措辞可直接作为 mcbot 的评审清单项。执行期预计算下一段 + 平滑接段，是消除"走走停停"观感的关键。

### 4.5 身体与区块票据

- 假玩家因为被移出客户端区块跟踪机制，**不会自动带加载票据**；因此另加一个**自过期区域票据**：半径 2 chunk（5×5 已加载垫），票据带 40 tick 超时、每 20 tick 或跨 chunk 时续期；同伴一停止 tick（休眠/死亡/崩溃），票据自然过期——**没有任何显式释放，也就没有泄漏与"忘了摘"**。多同伴共享 chunk 时共享一张票。
- 客户端侧另有一层"心跳目标"：处于"可打断的工作"状态的同伴 UUID 集合被持续保活（模型思考期间也要保持加载）。

**Why it matters for mcbot:** 自过期票据优于显式 acquire/release 记账——mcbot 的 chunk-ticket 管理值得对照这一条，确认"异常路径不会留下票据"。

## 5. 延迟工程

1. **流式默认开**（含用量帧），增量同时喂 UI 打字机、思考流与流式语音（按句切分边生成边播）。但**派发不在流内提前**——见 §1.4。
2. **只在"流开始前"重试**：连接错误/超时/可重试状态码按指数退避加抖动重试，尊重服务端的 Retry-After 上限；**一旦首个流事件已送达调用方就绝不重试**（token 已消耗），把部分结果交给回合层丢弃并整轮重跑。另有 90 秒的**块间空闲看门狗**（JDK 的请求超时只覆盖到响应头，卡死的 SSE body 否则会永久挂住）。
3. **提示词缓存纪律**（参考项目最强的一条工程实践）：系统提示层只放**会话内稳定**的内容（人设 + 操作核心 + 技能表 + 本能名册 + 延迟工具目录），**凡是会随世界变的东西一律不进系统提示**，改注入到用户回合（已使用过的工作站坐标就是因此从系统提示挪走的）；工具表按注册顺序恒定，因为**工具 schema 也是缓存前缀的一部分**；插件贡献的每轮状态片段明确"挂在请求末端，字不入会话历史"，因此"随便变也打不碎缓存"。
4. **缓存浪费诊断器**：逐轮比对"上一轮提示词体量"与"本轮实际缓存读取量"，差额（扣掉分段粒度噪声底 ~1k token）即"本该命中却重新处理"的 token 数；它是**诊断而非统计**——这个数一涨就说明前缀被谁动了（系统提示改了/工具清单变了/历史被从中间剪了/隔太久过期了），平时应接近零。刻意**不折算金额**（价格表维护不起）。
5. **受理即回执的异步任务**本身就是延迟工程：长活不冻结回合（见 §3.3）。
6. **收尾事件顶替最后一次工具往返**：任务完成的事件发生在"任务态"，按三态路由自动落进"立刻开轮"档，因此它不是新增开销，而是替代同步模式里那一次结果往返。
7. **不设工具回合硬上限**（省掉反复确认与人为节流），失控交给"主人中断"与长期目标的轮数保险丝。
8. **目标评估器单独一次调用**：判"目标是否达成/是否原地打转"用一个独立的小请求（不许调工具、只回结构化判定），只喂限量窗口（约 8KB 对话、每行截断），**只计新处理 token 入账**。

**Why it matters for mcbot:** mcbot 已有 prompt-prefix 缓存，但参考项目的**缓存浪费诊断器**（可度量化、有噪声底、不报金额）是"缓存不静默退化"的钥匙——prefix 缓存最怕的是某天有人往系统提示里塞了一个会变的字段，而这个指标会立刻现形。另注意它把"用量帧"当作**自动压缩的触发信号**（API 数的，不靠客户端估算），比本地估算稳。

## 6. 游戏内 UI / UX

- **主面板（默认 G 键）**：一只同伴一个面板，三个标签页（聊天 / 物品 / 设置）；左轨是同伴花名册（头像点选、"+"召唤、"✕"遣散）；聊天页左为可滚动文字记录（气泡、工具调用带转圈→打勾状态，**原始工具结果 JSON 不显示**，只用于翻状态），右为"计划卡"（读物理记录里的最新待办，故压缩后仍在）；物品页是仿原版背包的只读角色页（打开时定时刷新）。
- **轻量交互三件套**：R 键按住出同伴选择轮盘（滚轮/指向选人，松手确认）；Y 键对"当前交互对象"弹一行极简输入框，回车即发即关屏；V 键按住说话（对讲机式，松手发送转写）。默认键位避开原版占用，且注册进原版 Controls 的独立分类可改绑。
- **头顶气泡**：两条独立线——"说的最后一句"（按字数给寿命，超时消失）与"此刻在干什么"（有工具在跑就显示工具名，只是在等模型就显示"正在思考中"）；两者互不遮挡。**状态驱动而非事件驱动**：渲染方逐帧现算，不靠推来的事件记状态（文档记载旧实现因事件被吞而丢状态）。气泡只在主人自己的客户端存在，**不走网络**（对话内容是主人的私事，曾经气泡是唯一的泄露通道）。
- **HUD**：通知条/toast（回合失败、断连等），左侧缘可滑出的肖像 HUD，准星提示层（命令回话用它闪一下）。
- **设置页**：十个分页（模型、语音识别、语音合成、人设、档案、皮肤、主题、技能库、外接大脑、MCP），表单面板、下拉、滑条、确认对话等零件都在 `ui/` 工具箱里且有单测。
- **人类干预**：一个"Stop"物理开关（队列外），取消未决调用 + 叫停身体任务 + 释放任务作用域的手持意图；死亡/断线有独立的静默路径（**主人离线不叫停身体**——任务照跑完，收尾进离线出箱等主人回来）。设置改动（provider/key/模型）即时生效：清空 LLM 客户端缓存，下一轮重建，不必重启游戏。
- **确认/澄清**：不可逆的**主人操作**（遣散同伴）走模态确认卡；**委托给 agent 的物理动作没有逐条确认 UI**——破坏性路径的"授权"是在模型侧用参数表达的（见 §3.3）。澄清方式是纯对话："请求太含糊就问清楚，不要猜一个工具或查状态假装在忙"。
- **外部脑接入**：设置页有端点/令牌显示与复制，另有一个"复制接入提示词"按钮——把"我该写哪个客户端配置文件"外包给用户自己的 AI，提示词内嵌端点与令牌，并当场警告"这段话等于操控权"。

**Why it matters for mcbot:** R3 的面板清单可以照此对齐（转录 + 计划卡 + 工具调用状态 + 只读背包页 + 设置分页 + 接入提示词），并可采用两条被验证过的细节：**(a) 工具结果 JSON 不进 UI**（只翻状态，保持可读）；**(b) 气泡/状态线"状态驱动、逐帧现算"**，避免事件丢失导致的悬空 UI。另外"复制接入提示词"是零成本的 onboarding 机制，mcbot 的桥接文档可直接采用这个形态（但**必须自带令牌泄露警告**）。

## 7. 记忆 / 持久化

### 7.1 会话日志（M5 的 JSONL 参照）

- 每同伴一个 append-only JSONL：一行一条判别式记录（头部/用户/助手/工具/事件类），另有格式版本号与迁移逻辑；加载有默认条数上限。
- **两个视图同源**：LLM 视图（压缩后）与显示视图（物理记录）——压缩、清空、人设切换在显示视图里渲染成**分隔线**，不删任何历史。**事件不进 LLM 视图，只在显示视图留痕**。
- 落盘即时（每次追加即写）；容错取向明确："坏行跳过、读不了当空箱、写失败只记日志不打断对话"。
- 启动时扫描**未答复的工具调用**并合成取消结果，修复被打断留下的悬空调用（否则下一次请求会被上游拒）。
- 事件/收件箱另有自己的 JSONL（整本快照重写，空箱不留空文件），用于"关游戏时没来得及消费的输入下次还在"。

**Why it matters for mcbot:** mcbot 的 M5 JSONL 可直接采用"append-only + 判别式行 + 显示/模型双视图 + 坏行跳过"四点；其中"压缩/清空/换人设都是**分隔线而非删除**"和"启动修复悬空工具调用"是两处容易漏掉但很关键的细节。

### 7.2 压缩（compaction）

- 触发阈值的判据是**上一次请求的真实提示词 token 数**（API 数的），靠近模型窗口时先压缩再发本轮；后端不报用量时退化为本地粗估（全仓唯一一份估算口径：CJK ≈ 1 token/字、ASCII ≈ 4 字符/token、每条消息固定结构开销）。
- **保留近段原文**：只总结更早的部分，最近约 20k token 的消息逐字跨过压缩边界（"主人刚说的话和她刚给的回执不会被压成转述"）。
- **切点规则**：保留段的第一条只能是用户消息（轮边界，首选）或助手消息（单轮超预算时的劈轮点），**永远不能是工具结果**——工具结果必须跟着它的调用走，拆开下次请求即 400；预算内找不到合法切点就退化成全量总结。
- 摘要请求有独立系统提示，用**两步输出**引导：先在草稿标签里逐条核对（指令/坐标/物品数量/失败教训），再在正式标签里按固定结构输出（主人指令与意图、世界知识坐标、自身状态、已完成、失败与教训、待办、当前工作与下一步），并明确"标签之外不许输出、不许调工具"。
- 压缩有**代数戳校验**（中断即丢弃）、**连续失败熔断**（3 次后不再自动尝试，历史不受影响）、进度反馈（按流式字符数做指数饱和的进度值）、手动/自动共用同一条出口（手动压缩不看"最少条数"门槛）。
- 压缩边界先写进 JSONL（**重启重放的是压缩后视图，压缩前原文留在文件里当档案**），再替换内存上下文。

**Why it matters for mcbot:** mcbot 已有会话压缩；可对照补齐的是 (a) **以 API 用量为触发信号**、(b) **保留近段原文**、(c) **切点不得拆散"调用—结果"对**、(d) **失败熔断**、(e) **压缩边界落盘以实现可重放**。这五条都是"踩过才知道疼"的类型。

### 7.3 事件/收件箱（R2-S4 的配送面）

- 每同伴一个队列，**主人的话与世界事件共用同一条线**，push 即落盘、消费即清（跨会话不失忆）。
- **消费时机由"发生时大脑的状态"决定，而不是由输入类型决定**：回合进行中→进箱躺着，在工具批结算的边界一次倒空；后台任务执行中→立刻开轮（"任务期间发生的事是军情"）；完全空闲→进箱等下一个轮子搭车。唯一例外是"活人在说话"（主人本人/桥接的真人消息）在完全空闲时也开轮。
- **倒箱 = 拼一条用户消息**，固定顺序：状态快照（消费瞬间现取）→ 事件（按到达序）→ 主人的话压轴；躺超过 10 分钟的条目**标注年龄**（跨会话恢复的旧闻尤其要紧）。
- 队列有上限（约 200 条），满了丢最老的并**记账**，倒箱时如实补一句"你看到的可能不是全部"。
- 队列本身是**纯台账不是调度员**：不认识游戏、不认识回合、不认识条目类型，只回答"现在熟没熟"；"消费者能不能来取"是消费者自己的停牌（死亡、被外部脑接管），不是队列的事。
- 急件叫醒采用**脉冲可丢、电平不骗**：急件落地时同步通知等待者"来问吧"（不递事件），正确性从不依赖叫醒——需要时随时可问、答案一致，丢一次叫醒下次一问就发现。因此不存在"错过的排空"，也不需要记住"我刚才想排空"这种会出错的状态。
- 所有事件的 kind 在一个登记处收口（XML 组装/转义/游戏时间戳都在那里），**禁止散装手搓事件字符串**；入口不管时机（何时被消费由队列规则决定，事件类型没有贵贱之分）。
- 另有"定时器"机制：不占身体、不进任务槽、当场返回；记的是**主世界游戏刻的绝对值**（世界不跑表就不走、重启不重新计时），跟存档落盘；到点发一条急件事件。它被明确限定为"给世界不会主动通知你的事"（炉子、庄稼、天亮），"自己派出去的活用表去盯就是把轮询换了个马甲"。

**Why it matters for mcbot:** R2-S4 的"任务事件"如果只有一条通道很容易长歪；这里的**三态路由（按大脑状态而非事件类型）**、**倒箱拼一条消息（避免挨着的两条 user 消息被上游拒）**、**有界队列 + 丢弃记账 + 年龄标注**、以及"叫醒只是脉冲、状态才是真源"四条，都是可以整体搬走的架构决策（**搬决策，不搬代码**）。

### 7.4 长期目标

- 目标是**跨轮存活的那一件事**：每轮结束由客户端把目标与进度重新递到模型面前，直到达成/连续判"原地打转"/跑满轮数/主人喊停。
- **没有状态机**：只有"在"与"不在"，四种终止方式结果都是清掉，区别只在告诉主人的那句话；**刻意不留"暂停中的目标"**（想继续就再说一遍，成本是一句话；中间态要配一整套动词，每个动词又得回答"从哪儿能到哪儿"）。
- 有轮数硬上限（30）与 token 记账；上限的理由写得很实在：一轮主请求本身就是数万 token，到顶的意义是**停下来让主人看一眼**而不是闷头烧。

**Why it matters for mcbot:** 若 mcbot 考虑"长期目标"功能，这个"没有暂停态"的取舍能省掉一整套 API 面；而"把目标评估外包给一次小请求"比在提示词里祈祷模型自己判断更可靠。

## 8. 其它值得考虑的 / 该刻意避开的

### 8.1 值得抄的（机制层面）

1. **插件一扇门**：对外只暴露一个注册接口（注册工具 + 打包技能目录 + 订阅生命周期事件 + **贡献每轮状态片段** + 配置目录 + 仅客户端块），内部照旧用各自的类。其中"贡献状态片段"明确挂在请求末端、不入历史、因此不破坏缓存——这是 mcbot 桥/扩展点可以直接采用的设计。
2. **技能包**：多层目录 + 就近覆盖 + jar 内置；系统提示只列摘要，正文按需加载。成本极低的知识注入通道。
3. **MCP 双向**：既能连外部 MCP 服务器（把对方工具注册进全局工具表，内置大脑自动看见，支持运行时启停与状态徽章、退出时杀子进程），又能自己起 MCP 服务器让外部脑接管。mcbot 只做"服务端"的话，此处的**运行时工具表变更 + 面板状态**值得对照。
4. **工具名宽松匹配**：模型把工具名大小写写错时静默纠偏而不是崩回合（文档点名参考了某开源编码 agent 的同类做法）。
5. **schema 是代码也是校验器**：参数结构在构建期就限定取值/范围，非法名在注册时立刻炸（避免整轮 400）。
6. **数据生成标签**：把"脚手架材料/可破坏/可穿行"等语义做成标签数据生成，而不是散在代码里的硬编码清单。
7. **无头测试为重 + 游戏内测试为辅**：大量纯 JVM 单测（含用假体素网格驱动寻路的测试）+ 少量带结构文件的游戏内测试；重构日志里逐项记录"哪个测试钉住了什么"，并诚实记录测试缺口。
8. **UI 与资产有独立工具链**：`ui/` 纯逻辑可单测；美术资源用 HTML 模板 → 像素图（PNG）的生成管线，保证像素风格一致、可重生成。
9. **模型/站点/上下文窗口外置为 JSON 并复制到用户目录**：上下文窗口用于自动压缩阈值，用户可加站点/改 URL/加模型级生成参数。
10. **请求 id 贯穿日志** + 每轮一行摘要（耗时/块数/用量/结束原因/工具名）——多同伴并发时这是唯一能对账的东西。

### 8.2 陷阱 / mcbot 该刻意避开的

1. **别让长任务冻结串行工具派发器**：参考项目的派发器是严格串行（一件结果落地才派下一件），因此它必须把无界长活改成"受理即回执 + 后台"；若照抄串行派发器却没配套异步任务，一个几分钟的 `move_to` 会把整个回合卡死。
2. **别为每种机器写专用工具**：参考项目**没有 smelt 工具**——熔炼/切石/锻造被表达成"查配方拿到配方类型与操作指引 → 对工作台/熔炉交互 → 转移物品"，靠通用交互 + 容器/菜单抽象覆盖所有模组机器。mcbot 若打算加 `smelt`，先确认通用路径真的做不了（否则会得到一个需要为每个模组维护的专用工具集）。
3. **缓存前缀纪律要可度量**：系统提示里任何"会变的东西"都会静默毁掉 prefix 缓存。要么像它一样把可变内容全部挪到用户回合/请求末端，要么建一个同类诊断指标；只靠代码评审守不住。
4. **压缩不能从中间剪**：切点必须落在轮边界，且**绝不能把工具结果和它的调用拆开**（上游直接 400）。
5. **别把节点上限当 CPU 上限**：会造成"误判无路 → 正确的目标被拉黑 → 舍近求远"这类**持久性错误**。CPU 归线程池与优先级管。
6. **别追求"更精细的画面"**：高度图被明确否决（表达不了悬挑与头顶净空），稠密体素太重。少层水平切片 + 塌成一个移动性符号是已被论证的中庸。
7. **粗层的启发式不可采纳，不能当正确性来源**；"封死/无路"这类结论**宁可漏报不可误报**（误报会触发错误拉黑，比慢更糟）。
8. **快照体系的上限要认得**：它每 tick 整体重建、不做失效追踪，因此第三方改方块最多陈旧约 1 秒。同伴场景可以忍；若 mcbot 要做高频/多主体共享缓存，得重新设计而不是照搬。
9. **自过期票据优于显式释放**：显式 acquire/release 在异常路径（崩溃、被杀、死亡、换维度）必然漏。
10. **"唤醒经济学"值得内化**：任何"主动打扰模型"的功能都该先回答"这次唤醒在替谁花钱"——替任务花不必唤醒（工具结果本来就会送达）、替身体花交给本能层、只有"陪伴感"这类产品功能才该用急件通道且必须可关。

## 10. 一句话总结

这个参考项目对 mcbot 最大的价值不在代码，而在**几条已被实测过的架构决策**：① 系统提示字节级稳定以保住前缀缓存，并配一个可度量的"缓存浪费"诊断；② 长活统一走"受理即回执 + 收尾改事件"，且用**本地可判**的判据拒绝"同一批第二个派发"；③ 事件用**三态路由（按大脑状态而非类型）**并配"脉冲可丢、电平不骗"的唤醒模型；④ 空间感知用**自我中心语义字符网格 + 危险膨胀 + 与寻路同谓词**，并明确否决高度图与稠密体素；⑤ 寻路用**有界池 + 冻结快照 + 只读已加载视图 + 粗层只作引导、封死宁可漏报**。它**没做**的恰好是 mcbot 的 R2-S3（流式内提前派发）——所以这一项只能靠 mcbot 自己设计，可借鉴的只有它的 SSE 增量累加器与"流开始后不重试"的边界。
