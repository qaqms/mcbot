## 权限与物品

### T02 只拾取与只读权限

首轮箱子往返、换主手及拾取已有认可，不因本文再跑整项。
collect改变地面物品和同伴背包，属于修改动作；即使同伴不走路，也不是只读查询。
当前任务包含“只读”“不要移动”或“禁止移动”等已识别短语，会整项归为只读，
因此collect、transfer和equip都可能在客户端派发前被拒绝。

单独的collect只处理当前身体局部范围内的掉落，不执行move_to或寻路；
超距返回OUT_OF_REACH，不会在这个工具内部先走过去。
但是普通任务仍允许模型选择其他工具，不能把“不移动”等未识别措辞当作可靠权限边界。
当前没有“允许拾取、禁止移动及其他修改”的独立权限模式。
需要这个硬性保证时记录功能限制，另行评估，不通过删标记、改说法或伪造参数绕过只读。

若维护者安排普通拾取复测，保留实际任务原句、实际工具列表、同伴前后位置、
背包/地面数量及拒绝原文。没有目标、背包空间不足和只读拒绝分别记录；
ok=false也可能已拾取一部分，以实际collected_count/remaining_count及现场为准。
首轮“不移动”原句和后来的“不要移动”改句不能混为同一任务对照。

## 三类炉子的判读

### T08 熔炉空槽与燃烧余量

三槽为空只表示原料、燃料物品和产物槽都空，不表示剩余燃烧时间为零。
已经消耗的燃料可能仍提供燃烧余量；火焰、界面进度和smelt query的实际计数分别记录。
原料取空或任务取消不会由mcbot强制熄炉，原版机器仍按世界tick运行。
先前基本烧制已认可，本说明不强制再烧一批。

如复测，保留load、query、take回执、三个槽和背包前后数量，
另记burn_remaining_ticks、cook_progress_ticks及cook_total_ticks。
等待40秒不是出货证明；查询成功也不保证已有产物或仍在烧制。
没有真实计数时写未记录，不能凭空槽或模型叙述填“已熄炉”。

### T09 高炉使用自身真实计数

高炉也适用“空槽不等于熄炉”的说明。
保留高炉自己的槽位、燃烧/烧制计数、产物与背包对照，
不能用熔炉的数据替代高炉，也不把等待25秒当作固定完成承诺。
首轮高炉基本烧制已认可，没有新异常时不重跑。

### T10 烟熏炉使用自身真实计数

烟熏炉也适用“空槽不等于熄炉”的说明。
记录这台烟熏炉实际生牛肉减少、熟牛肉增加及燃烧余量，
不把燃料槽为空说成机器已停止燃烧。首轮基本烧制已认可，没有新异常时不重跑。
取消停止后续工具步骤，不回滚装料/取出，也不会替原版停止机器。

## 权限拒绝与流程

### T11 客户端与服务端拒绝分开记账

客户端预派发只读拒绝的原文为：

```text
DENIED:主人要求只读，此任务不能移动或改动世界/物品。
```

这种拒绝没有发送对应动作tool_call，不能证明服务端权限门被实际触达。
服务端动作门的通用文案为：

```text
DENIED:当前任务权限不允许此动作；只读任务只能观察，不能移动、换装或改动世界/物品。
```

服务端这一文案还用于失效任务、身份/维度不匹配等拒绝，
所以必须看permission_denial.gate=server_action及reason=READ_ONLY，
并核对seq/task/tool/维度，不能仅看句子就记服务端只读通过。
限流、白名单、owner、参数或距离拒绝也不等于只读门拒绝。

T11的确定性补测仍使用 `docs/REAL-GAME-RETESTING.md` 中的
`/mcbot verify_readonly`；无同伴/已有任务等前置阻塞先整理现场。
模型未调用、客户端拦截和服务端READ_ONLY三种证据单独记录，不互相代替。

### T15 workflow由客户端编排

workflow是客户端本地工具，整份清单由AgentRunner/BoundedWorkflow校验、逐步推进；
它不是发给服务器的一个外层workflow任务，也没有一次性提交清单后让服务器独立跑完。
每个实际子工具仍带同一task_id经过正常服务端派发、权限和资源检查，
前一步取得真实终态后才推进下一步。

整份清单参数或只读预检拒绝发生在客户端，可见“流程参数无效”或
“只读任务的流程包含动作，整份未执行”；此时不能写服务端执行了第一步。
子工具在服务器因BUSY、参数、范围、权限等拒绝时，
记录该步工具、seq、反馈及已有步骤效果；不能把所有workflow失败都归为客户端问题。

成功数表示已有步骤的实际终态，不表示主人最终目标一定实现，
也不把请求数量当原版消耗或产量。取消保留已执行效果和在途未知，
停止后续步骤，不能回滚已放方块、已搬物品或让炉子熄灭。
原T15三个场景已有认可，本文仅澄清责任层，不扩大清单或重复已认可场景。

## 待答后重载

### T16 两分钟内保存，隔离TIMEOUT

首轮T16已有认可；后续需要复测时仍分两趟，不同时换模型。
第一趟原任务为：

```text
@bot 用ask_owner问我“下一步查看背包还是扫描附近”，等回答后只执行选择的一项。
```

实际问题出现后答 `@bot 答 查看背包`，核对只续跑一次；
结束后重复同一答案，不能创建新任务或再次执行inventory。
G任务框发任务时删去@bot前缀，聊天回答保留 `@bot 答`。

第二趟重新发同样任务，不回答，按以下顺序操作：

1. 先确认实际ask_owner/question已生成且仍在等待，记录question_id和生成时间。
2. 从问题生成时刻起，在120秒内完成G → 模型 → 保持配置不变 → 保存并应用。
   建议看到问题后立即操作并在60秒内保存，给操作和时钟差留余量；
   时限不是从发原任务或打开面板时开始算。
3. 保留重载造成的旧任务CANCELLED及旧问题清理证据，再答 `@bot 答 查看背包`，
   旧回答应拒绝且不新建任务。
4. 在同一世界直接发新的 `[只读]只查看自己的状态。`，
   核对新任务真实status回执与正常终态，不用状态按钮代替。

如保存前已经出现TIMEOUT，重载因果子项记阻塞，本轮不能证明保存清除了待答问题；
保留其他有效证据，整理后另开一趟并记录新的问题编号。
不要为了“延长等待”暂停单人世界、切后台或换配置；
超时使用客户端时间，世界暂停不能可靠保留问题。
记录问题生成、保存、CANCELLED或TIMEOUT、旧回答拒绝和新任务的各自时间及日志定位。
回答等待期限不由本说明改变，也不要求专门等两分钟遍历所有过期组合。
