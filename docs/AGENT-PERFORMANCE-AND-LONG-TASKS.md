## 2. P0：已修复的流式参数匹配

原StreamingTurnReader按tool_call的index选工具定义的required字段。
这个index表示本轮调用位置；目录首项workflow要求steps，
而本轮第一个调用可能是inventory、find_resource或break_block。
合法参数因此过不了错误的必填表。目录首项没有必填时，
另一个工具的残缺参数又可能被误判就绪。
旧回归的目录与调用恰好同序、同工具，没覆盖实际目录的组合。

现在按工具名称查必填表，按本轮index保留各自的拼接状态；
名称晚到时回放已经收到的参数，未知工具留给正常整轮处理。
只在ID到齐、累积参数与已检查对象一致时发布就绪，
异常的两个独立对象不能借扫描器重置冒充合法完整参数。
已就绪槽按实际index顺序报告，每槽只报告一次。

保持AgentLoop只早派发index0，其余调用等待前项终态；不改权限、工具定义、
身体调度、重力、材料与桥v1.0。提前启动仅能把完整参数到达后的流尾等待
与工具执行重叠，不能省去参数生成前的等待，也不能自动减少模型轮数。

新增11项：读取器9、实际SSE解析接AgentLoop1、生产ClientToolDefs目录1。
旧实现先取得7项失败；修复后70项专项和656项全量离线回归通过。
没有调用真实模型；离线断言证明EOF前启动与恰好执行一次，
不证明该提供商的实际提前量。下次现场对照同一attempt的
first_dispatch与stream，派发早于流结束才是实际重叠的证据。

## 4. 参考副本呈现的机制

只读核对实际实现，不以设计稿或README描述代替已接线源码：

- 请求组装仍取完整工具目录；当前并不是每次先搜索再展开工具。
  技能目录只列用途，正文和附属文件通过本地工具读取；
  API功能组有索引，详细用法在需要时读取。
- 程序执行支持本地条件与循环；一个模型调用能用扫描结果连续安排移动、
  挖掘和拾取。运行有调用数、时长、指令量与输出预算，出错和停止有真实回执。
- 长期目标订阅一次运行结束，再用目标、当前身体与近期证据判断是否续跑；
  有累计轮次、无进展和主人停止的边界，目标可落盘。
  这种独立模型评估也增加调用和费用，不适合照搬到可精确判定的物品计数上。
- 模型请求边界能整理历史；旧摘要有单独的更新路径，近期消息保留更多。
  具体窗口、预留量和保留量服务于它的请求体量，不能直接套到本体。
- 跟随是游戏刻驱动的身体任务，目标移动时重定向，接近后休眠；
  战斗任务自行追击、保持攻击节奏。危险响应可以借同一战斗实现接管身体并交还，
  不是让模型每次决定转头和出手。

对应读过的源码入口为AgentRequestContext/SystemPromptComposer、SkillTool、
GoalSteward/GoalState、Compactor、ScriptTool/ScriptLimits、work.lua、
FollowCompanionTask、AttackCompanionTask和MobDefenseChain。
这里只归纳机制，没有引入上述实现或文字。

参考有挖10个铁、挖深处单颗钻石的场景和长期目标测试代码；
本轮没有运行它们，没有取得自由世界自主采集64颗钻石的实机成绩。
危险响应读到的是同伴自身附近威胁，不能据此认定护卫主人已完整实现。

工具懒加载应按总任务成本决定：省下的输入处理与避免误选，
要与新增发现轮次、缓存前缀变动、整理后的重新发现相抵。
当前17个工具不是先引入搜索闸的充分理由。
优先减少无必要模型往返、加载不相关技能正文和无进展动作；
工具数量明显扩大时再比较全量稳定目录与按任务固定分组的实测结果。

## 5. 分卡实施建议

### LT1：目标事实与任务内上下文

在现有AgentLoop/AgentRunner上增加明确目标、当前子目标、数量基线、
累计实际成果、失败原因及预算。普通聊天结束沿用现状；
可验证任务的自然语言结束必须经过实际状态核对。
例如“新增64颗钻石”比较相对基线的实际入包量；
“包里达到64颗”比较当前总量；“交给主人64颗”需要真实交付证据。
目标口径不能由内部自行互换。

请求前预算必须包含system、技能索引/正文、工具定义、临时身体状态、
历史和输出预留。不拆assistant/tool组，只在完整结算边界整理。
整理失败保留原文；确实装不下则明确暂停，不能继续付费撞上下文上限。
当前目标和实际进度从结构化账本重新注入，不受自由文本摘要删减影响。

技能目录可逐步改为稳定用途索引和白名单本地读取，保持现有玩家技能兼容。
不为17个工具强制添加发现轮次，不把技能正文当权限或硬完成判据。

LT1验收：模型提前说完成仍能继续；多段真实计数不丢；工具配对完整；
小窗口/无usage/摘要失败可控；取消后不自动续目标；
原桥只在整个目标满足或终止时发done，段末汇报不提前发done。
该卡不新增自主找矿、跟随或战斗行为。

### LT2：有界连续采集与必要的探索

先做已加载区域内的材料采集：检查实际工具/空余空间，选目标，
规划可工作站位，等移动终态，复核视线，挖掘/拾取，更新实际物品进度，
再挑目标。移动/挖掘仍用现有服务端守卫，不能平行操纵同一具身体。
路径中途下落与目标变化沿用重力和重规划事实，失败保留已取得的物品。

区域耗尽、空间/耐久不足或需要新权限时返回结构化阻塞原因，
让模型只在这些决策点补计划。无进展按世界/物品事实判断，
不能靠反复改半径或重发动作刷新预算。
初版可用明确Java任务状态实现，不先扩大到任意脚本或解释器。

再补限定区域/深度的探索：记录覆盖区域和未知边界，在真实位置变化后换区域；
若要勘探挖掘，必须明确勘探目标和具体允许的改动范围。
目前“不靠挖掘探查”与具体路线授权是有效规则，
不能为了长任务静默删除、把一句“采钻石”解释成任意开洞授权。
希望减少人工干预时，需要独立设计主人预先授予的任务范围及服务端逐动作校验。

条件具备时推进到钻石任务：准备工具/材料，进入合适的已授权区域，
采集并核对实际掉落，缺矿再探索，包满或工具将坏时处理补给，
满足原目标后返回或交付。矿块数不能当钻石件数，
精准采集/时运、留地物和原有钻石要按实际物品事实分别记账。
食物、光照、危险和返回能力也须说明是否已有，不用提示词掩盖缺项。

验收逐级从16份木材/圆石、带遮挡与移动的采集、已知矿脉64份材料，
到限定野外区域自主采集钻石。每一级保存真实数量、失败恢复、取消和预算证据，
不能用预放64个矿的测试代替自然世界找矿。

### 已确认的复用阻塞

1. 被动拾取缺失把每次触碰变成显式子调用，模型还会逐次安排。
   本卡把自动触碰接身体，把远处物品的走近留给任务，按实际背包结算。
2. 修复前AgentLoop每次gather都调用set_goal，而set_goal只允许一个固定物品条件。
   最终条件设钻石剑后，采木头就被拒；先采木头又把最终条件锁成木头。
   这属于目标作用域错误，现通过显式scope=subtask解耦，不靠换task_id规避。
3. 旧workflow没有读取返回值决定参数的能力，材料缺口、合成后槽位和站位变化
   都要回模型；这比“单个工具执行慢”更直接影响复杂任务总时长。
   新run_program补同一通用机制，保留workflow兼容，不为各成品另写执行器。
4. 完成验证只认物品入包，建筑、交付、地点、击败目标没有各自证据；
   这些目标仍可能按纯文本结束，不能承诺任意长目标已可靠完成。

### 实施顺序和验收边界

- 第一卡：自然触碰拾取，已实现；原版规则与只读限制保留，验证不依赖collect，
