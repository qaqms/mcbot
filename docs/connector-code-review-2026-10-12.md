## 优先修复

### 1. 反问消息没有提供回答所需编号

连接器 `service.py:779` 收到并缓存 `question_id`，但在 `service.py:795` 发给宿主的消息中，
只带裁剪后的问题文字；`prompts.py:134` 的模板也没有编号。
入口 `__init__.py:123` 的回答 Schema 要求 `question_id`，
`service.py:909` 的状态输出只有待答数量，没有编号或问题明细。

**复现**：收到问题编号 `qid-927` 后，检查实际发出的宿主消息；
编号没有出现在其中。用户回答“确认”时，宿主模型无法从这条消息取得准确编号，
需要猜测或缺参，不能完成可靠的路线/攻击确认。
原有问答测试直接把测试编号传给 service，没有验证模型是否能获得编号。

**改进**：在模型能读取的消息或结构化上下文中保留准确的
`session_id`、`task_id`、`question_id`，明确它们仅用于回答关联，不能让模型代答。
用户听到的自然语言不必念编号；回答须绑定仍有效的问题，不能用最新编号替换旧问题。

### 2. 授权问题被裁剪，用户看不到完整清单

同一处 `service.py:800` 把问题裁为前 400 字符。
本体 C3 的问题可能包含完整服务端路线/目标改动清单；
尾部丢失后，用户口头确认的范围与服务端实际批准范围不再一致。

**复现**：发送末尾含独立目标标记、超过 400 字符的授权问题；
编号仍留在连接器缓存，但实际宿主消息没有尾部目标。

**改进**：授权问题完整保留，长清单用可查看的完整展示配合明确确认。
不能用静默截断后的摘要请求批准；无法完整呈现时应阻止授权并提示缩小任务范围。
不要为消除长度问题而放宽本体授权检查。

### 3. 指定取消会错误释放其他任务

`service.py:873` 调取消接口后不检查返回的 `ok`，
随后 `service.py:876` 无条件把当前本地任务记作 cancelled。
`__init__.py:355` 还把字符串、布尔等非法编号降级为缺省，
而缺省在传输层是取消全部，不是“参数错误”。

**两组复现**：本地跟踪任务 11，取消未知编号 999 返回 `ok=false`，
或成功取消另一个排队任务 22；两种情况下任务 11 都被本地释放并标为 cancelled。
本体仍可能执行任务 11，后续再派活会失去原任务约束。

**改进**：按目标编号和 `ok` 处理；取消其他任务不清当前槽，未知编号不报成功。
非法显式编号应返回参数错误，不能扩大为全部取消。
缺省/0 的全部取消可以按既有契约执行；
接口受理取消不等于已经独立确认身体停止。

### 4. overwrite 只替换本地记录，没有停止旧任务

`service.py:537` 将旧本地等待项标为 superseded，
但 `dispatch_claimed` 只发送新任务，没有取消旧任务。
这不满足 `__init__.py:158` 对 overwrite 的“停止旧任务并启动新任务”描述。
本体只在 PARK 时由新指令顶替旧任务；普通模型等待/执行状态收到新指令会排队，
不能依赖投新任务来保证所有情况下都已打断旧任务。

**复现**：任务 11 已派发并超过防抖时间，overwrite 后派发任务 12；
传输记录只有两次 POST，没有取消任务 11。

**改进**：若继续提供“打断”语义，先按编号发起旧任务取消，正确处理返回与未知结果，
再决定是否发送替换任务；旧编号尚未取得时也需要安全的处理分支。
不要把连接器自己释放等待项写成服务器已停止旧任务。

## 结果与事件

### 5. 本地等待超时仍使用“做完了”的提示

`service.py:588` 的看门狗使用 `CUE_DONE`；
`prompts.py:123` 的模板在各语言中包含“做完了/finished”及“已经停下来了”。
插入“先不等了”只改变中间正文，不会消除外层成功与停手描述。
这条路径仍可能造成 PR #5 P-2 的误导，同时 P-3 的任务仍可能在执行。

**复现**：离线缩短本地等待预算，未收到 done 后触发看门狗；
实际宿主消息同时出现“finished”“She has stopped”和“stopped waiting”。
缩短预算只用于可控测试，没有改变发行配置。

**改进**：独立表达“结果未知/仍可能执行”的超时通知，保留任务关联以处理晚到结果，
不要自动重投。900 秒配置确实已写入 plugin.toml/schema，但不能保证消除该路径。
service 缺省值及 README 配置表仍为 300 秒，后续顺便统一，不能只改默认值销账。
v1.0 的 status 没有历史终态查询能力，丢失 done 时不能靠活动计数猜旧结果。

### 6. 事件重复与处理失败可能造成重报或漏报

`service.py:663` 不按会话和 SSE id 去重；重复 done 可以再次发送完成通知。
`client.py:294` 遇处理异常后继续泵下一帧，
`client.py:308` 又把游标推进到后续成功帧，先前失败帧不能按旧游标补发。
插件重启或游标未正确确认时可能补发已展示的环内事件，
不能让旧通知重复改变宿主判断。

**两组复现**：同会话 id=66 的 done 发两次，产生两份完成通知；
另以 httpx.MockTransport 提供 id=10/11，处理 10 抛异常而 11 成功，
游标从 9 变成 11，跳过失败帧 10。没有真实网络连接。

**改进**：按会话/id 做有界去重，游标只推进到连续成功处理的边界；
处理失败可以断开补发或可靠保留待处理项，不能越过未处理事件。
`_push_cue` 吞掉推送异常也需要与事件确认策略一起核对；
可重放通知不能触发重复游戏任务，也不承诺宿主消息通道 exactly-once。

### 7. 不同任务的终态共用同一个合并键

`service.py:761` 为所有完成/失败通知使用 `mcbot_completion`，
问题也使用全局 `mcbot_question`。消息体没有提供可用于区分任务的结构化归属。
本地宿主已有按合并键保留最新消息的实现：
`app/main_server/character_runtime.py:1557`、
`main_logic/core/proactive.py:3383`。
因此，当不同任务的终态同时还在队列中，旧终态可能被新终态替换。

**复现**：任务 11 失败和任务 12 正常结束分别生成通知，
两者合并键相同。探针验证的是连接器输出；
队列覆盖风险由当前本地宿主代码支持，本轮未运行宿主进行实际投递验证。

**改进**：终态按会话/任务独立保存并投递，问题按会话/问题独立关联；
仅普通状态或可替代的进度快照合并。
问题结束/取消/过期时清理缓存及旧通知，避免把旧问题的回复送给新任务。
